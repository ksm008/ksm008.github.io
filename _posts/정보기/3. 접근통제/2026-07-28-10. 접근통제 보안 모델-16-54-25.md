## 1. 접근통제의 모델
### (1) 강제적 접근통제(MAC, Mandatory Access Control)
#### 1) 개요
- 보안 관리자가 취급인가를 허용한 개체만 접근할 수 있도록 강제적으로 통제함.
- 보안 레이블과 보안 허가증을 비교하는 것에 기반을 둠.
- 전통적 MAC 시스템은 다중수준 보안(MLS, Multilevel Security) 정책에 기반하며 서로 다른 분류 수준에 있는 데이터가 보호되는 방법을 지시함.
- MAC의 대표적인 모델은 BLP, Biba, 클락-윌슨, 만리장성 모델이다.

#### 2) 특징
- 주체가 객채로 접근하는데 적용되는 규칙은 보안전문가가 생성. 운영자에 의해 설정, 운영시스템에 의해 집행, 다른 보안기술들에 의해 지원된다.
- 중앙집중형 보안관리 시스템이다.
- 한 주체가 한 객체를 읽고 다른 객체에게 복사하는 경우 원 객체에 내포된 MAC 제약사항이 복사된 객체에 전파됨.
- MAC 정책은 모든 주체에 대해 일정하며 어느 하나의 주체/객체 단위로 접근제한 설정이 불가능하다. 
- 어느 한 객체에 접근하지 못하면 그 주체는 그러한 특정 비밀 등급을 가지는 모든 객체들에게 접근이 금지됨.

#### 3) 문제점
- 제한적 사용자 기능, 많은 관리적 부담, 비용이 많이 소모됨. 사용자 친화적이지 않음.
- DAC 시스템은 일반적 목적, MAC은 매우 특정한 목적을 위해 사용됨.
- 예시가 군 시스템.

### (2) 임의적 접근통제(DAC, Discretionary Access Control)
#### 1) 개요
- 허가된 주체에 의하여 변경 가능한 하나의 주체와 객체 간의 관계를 정의함.
- 주체 또는 그들이 속한 그룹의 신분에 근거하여 객체에 대한 접근을 제한하는 방식.
- 접근을 요청하는 주체의 식별에 기초하며, 임의적으로 어떤 객체에 대하여 주체가 접근권한을 추가 및 철회 가능.
- 세부적으로 신원 기반, 사용자 기반, 혼합 방식 접근통제 등으로 나뉨.

#### 2) 특징
- 중앙집중이 아님. 분산형 보안관리.
- MAC처럼 정적이지 않고 동적으로 정보에 접근이 가능.
- 윈도우, 리눅스, 매킨토시, 유닉스, DBMS 같은 대부분의 운영시스템이 DAC에 속함.
- 어떤 사용자들이 해당 리소스에 어떤 수준으로 접근 가능한지 볼 수 있음. 이게 DAC 모델의 ACL의 예시다.
- + 공개적으로 출시된 MAC 시스템은 SELinux, Trusted Solaris

#### 3)장/단점
- **(가) 장점**
	- 세분화된 접근제어가 가능하다.
	- 특정 객체에 대해 특정 주체(소유자)가 다른 주체에 대해 임의적으로 접근제어(접근 권한 부여)가 가능하여 유연한 접근제어 서비스를 제공 가능.
- **(나) 단점**
	- 사용자가 자신의 자원에 대한 접근 제어를 개별적으로 수행하기 때문에 전체 차원의 일관성 있는 접근제어가 부족하다.
	- 높은 권한을 가진 사용자가 다른 사용자에게 접근을 임의로 허용가능.
	- 통제의 기준이 주체의 신분이기 때문에 접근통제 매커니즘이 데이터의 의미에 대해 아무런 지식을 가지지 않음
	- 신분을 도용할 경우 결함이 발생함
	- 멀웨어는 DAC에 치명적. 바이러스, 웜, 루트킷은 DAC에 설치되어 응용프로그램으로 실행될 수 있음. 트로이목마 공격에도 취약하다.

#### 4) 임의적 접근통제 기법
- **(가) 접근제어 행렬(Access Control Matrix)**
	- 행렬을 이용하여 주체, 객체, 접근권한의 관계를 기술하는 방법.
	- 주체가 행, 객체가 열. 주체와 객체가 만나는 셀에 접근제어 정책을 기록하여 관리.
	- 효과적으로 권한 부여 정책을 정의할 수 있지만 주체와 객체의 수가 많아질 경우 크기가 커지므로 관리가 어려움.
	- 주체가 행, 객체가 열이기 때문에 비어있는 셀의 수가 많아지게 되어 공간상 비효율적인 문제가 있다.
- **(나) 자격 목록(권한 리스트)**
	- 권한 리스트, 티켓, 테이블에 대해서 설명함.
	- 권한은 주체가 객체에 대해 갖는 접근권한.
	- 자격 목록은 한 주체가 갖는 자격들의 리스트. 접근제어 행렬을 행 단위로 관리하는 것과 같음.
	- 권한 티켓의 형태는 콘텐츠의 보안성이 보장받지 못하는 분산환경에서 사용하게 적합함. 편리한 점과 불편한 점은 ACLs과의 정반대.
	- 권한 테이블의 예시는 커버로스. 커버로스는 사용하는 환경에서 사용자는 티켓을 받는다. 이 티켓의 사용자와 연관되어 사용자가 어떤 객체를 어느 수준에서 접근할 수 있는지를 지정한다. 접근통제는 티켓을 기반으로 함.
- **(다) 접근제어 목록(ACLs, Access Control Lists)**
	- 객체에 어떤 주체가 어떤 접근 권한을 가지는 지 명시함.
	- 객체를 중심으로 하나의 객체에 대한 접근권한을 갖는 주체들의 모임을 나타냄.

### (3) 역할기반 접근통제(RBAC, Role Based Access Control)
#### 1) 개요
- 사용자의 역할에 기반을 두고 접근을 통제하는 모델.
- MAC와 DAC의 접근제어 정책의 대안으로 제안됨.
- 권한을 역할과 연관시키고 사용자들이 적절한 역할을 할당받도록 하여 권한의 관리를 용이하게 하는 것. 
- 그룹의 개념과 가장 다른 점은 그룹은 사용자들의 집합이지만 권한의 집합은 아니다. (같은 부서 소속이라고 동일한 권한을 받지 않음)
- 역할은 사용자들의 집합이며 권한의 집합이다.

#### 2) 특징
- 주체와 객체가 어떻게 상호작용하는지 결정하기 위해 중앙에서 관리되는 통제 모음을 사용.
- 접근통체 수준은 사용자가 그들의 책임을 완수하기 위해 수행할 필요가 있는 운영과 작업에 기반.
- MAC, DAC의 단점을 보완한 기법.
- 인사이동이 잦은 조직에 적합하고 최근에 가장 많이 사용한다.
- 사용자에게 피할 수 없는 역할로 권한을 관리하기 때문에 Non-DAC라고도 불린다.

#### 3) 사용자, 역할 그리고 자원
- RBAC 시스템은 각각 사용자 대신 역할에 접근 권한을 할당함. 
- 사용자는 조직의 구성원이나 프로세스 등 조직의 자원에 대한 접근을 요청하는 모든 개체. 역할은 조직의 직무나 책임 등을 반영하여 설정한 추상화 개체로 설명할 수 있다.
- 권한은 조직의 자원에 대한 오퍼레이션의 관계를 추상화시킨 개체. 
- 사용자는 조직 내에서의 자신의 직무나 책임 등에 의해 적절한 역할에 할당됨.
- RBAC에서 역할과 접근권한 설정은 관리자에 의해 이루어짐.
- 사용자가 임의로 다른 사용자에 대한 접근권한을 설정할 수 없음
- 역할은 동적으로 변경될 수 있으며 사용자와 역할의 관계는 1:1일 필요 없음. 1:다도 가능.
- 역할에 할당된 접근권한은 상대적으로 자주 변경 X. 역할과 자원의 관계도 1:1일 필요 없음.

#### + RBAC의 3가지 기본 보안 정책 제공
- 특권의 최소화
- 직무의 분리
- 데이터 추상화

#### 4) RBAC의 장점
- 관리자에게 편리한 관리능력을 제공함. 비기술적 정책 입안자도 쉽게 이해가 가능하다.
- RBAC는 관리자에 의한 중앙 집중적인 역할 설정에 따른 접근 권한 설정을 함. DAC에 비해 유연성은 떨어지지만 일관성 있는 접근제어에 용이.
- 역할 수행에 있어 반드시 필요한 권한만 부여함으로 최소 권한 부여 원칙을 충족시키기 용이함.
- 역할 분리를 통해 접근권한을 명확하게 분리함으로 직무 분리 원칙도 충족시키기 용이함.
- 적용 사례로 미국 연방의료보험통상책임법을 뜻하는 HIPPA가 있다.

## 2. 보안 모델
### (1) 벨라파듈라 모델(BLP, Bell-LaPadula Confidentiality Model) - MAC
#### 1) 개요
- 비밀정보에 기밀성을 집행하는 상태머신 모델이며, 정보흐름 모델이다.
- 다중등급 보안 정책(Multilevel Security Policy)에 대한 최초의 수학적 모델.
- 현재 개발된 많은 MAC 기법들은 다중등급 보안 정책에 기반을 두고 있음. 따라서 MAC을 다중등급 보안과 분리하여 보긴 어려움.
- 컴퓨터에 저장된 비밀정보를 보호하기 위한 하나의 방법론이 다중등급 보안이며 이를 위해 개발된 최초의 수학적 모델이 BLP이다.

#### 2) 보안 규칙
- 기밀성 중심의 다중 수준 보안을 위한 요구조건의 일반적 기술에 의하면... 
	- 높은 수준의 주체는 낮은 수준의 주체에게 정보를 전달할 수 없다.
- 기밀성을 위한 다중 수준 보안 시스템은 다음 사항을 준수하여야 함.
	- No read up
		- 주체는 같거나 낮은 보안 수준의 객체만 읽을 수 있음. 자신보다 높은 수준의 객체는 못읽는다.
		- 단순 보안 속성으로 불림.
	- No write down
		- 주체는 같거나 높은 보안 수준의 객체에만 쓸 수 있음. `*속성`으로 불림. (star property)
	- 특수 `*-속성` 규칙 : 주체가 객체에 대하여 읽기, 쓰기를 할 수 있기 위해서는 보안 허가와 보안 분류가 동일해야 한다.

#### + 추가
- **주체와 객체의 Level**
	- 주체의 레벨은 clearance
	- 객체의 레벨은 classification
- **평정속성(tranquility property)**
	- 객체와 주체의 보안등급은 컴퓨터 수행과정에서 변경될 수 없다.
