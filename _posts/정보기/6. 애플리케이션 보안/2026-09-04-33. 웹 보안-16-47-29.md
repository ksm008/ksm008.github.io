## 1. 웹 보안 개요
#### 1) 웹 보안 위협
- 대충 웹을 많이 사용하게 되면서 노출이랑 유출이 많이 된다~
- 근데 그 이유는 TCP/IP랑 HTTP가 보안 서비스를 제공하지 않아서 그렇다

#### 2) 웹 트래픽 보안 방법
- 한 가지 방법은 IP 보안인 IPSec를 이용하기. 종단 사용자의 응용에 투명성을 제공함. 그리고 필터링 기능이 있어 선별된 트래픽에서만 보안을 처리하기 때문에 이에 대한 오버헤드만 추가됨.
- 또 다른 범용 해결책은 TCP 위 레벨에 보안을 구현하는 것. 가장 좋은 예시가 SSL(안전 소켓 계층Secure Socket Layer)과 TLS(전송 계층 보안, Transport Layer Security)라고 알려진 후속 인터넷 표준.
- IPSec는 선택적 암호화를 적용하는게 어렵다. 하지만 SSL/TLS는 선택적 암호화를 지원함.

## 2. SSL/TLS
### (1) SSL/TLS의 개요
#### 1) 기본 개념
- 클라이언트 서버 환경에서 TCP 기반 애플리케이션에 대한 종단간 보안 서비스를 제공하기 위해 만들어진 전송계층 보안 프로토콜. 애플리케이션에 대해 독립적이다.
- 대칭키/공개키 암호, 일방향 해시함수, 메시지 인증코드, 의사난수생성기, 전자서명을 조합하여 안전한 통신을 수행함.
- 특정 암호 기술에 의존하지 않는다. 특정 암호가 약하다고 생각되면 부품을 바꾸듯 다른 암호를 선택하면 됨.

#### 2) 클라이언트와 서버
#### 3) SSL/TLS 상의 HTTP
- 예를 들어 웹 브라우저로 신용카드 번호를 보내면 데이터가 클라이언트로부터 서버에게 보내짐. 이 때 도청당하면 정보가 넘어간다.
- 때문에 통신내용을 암호화해주는 프로토콜로 SSL이나 TLS를 사용함. 그리고 SSL/TLS상에 HTTP를 올림.
- 덕분에 HTTP의 통신은 암호화되어 도청을 방지할 수 있다. `https://`로 시작되는 애들.

#### 4) SSL/TLS 보안 서비스
- **기밀성 서비스**
	- DES, RC4 같은 대칭키 알고리즘을 사용하여 제공되며, 이때 사용되는 비밀키는 핸드셰이크 프로토콜을 통해 생성됨.
- **클라이언트와 서버 상호 인증**
	- 연결 과정에 인증을 사용한다. RSA, DSS 같은 전자서명 알고리즘, X.509 공개키 인증서가 사용됨.
- **메시지 무결성 서비스**
	- 해시 알고리즘을 통해 메시지 인증코드를 만들어 메시지에 포함시킨다.

#### 5) 암호 스위트(cipher suite)
- SSL/TLS에서는 사용하는 대칭키 암호, 공개키 암호, 전자서명, 일방향 해시함수 등은 사용하고 있던 암호 기술에 결함이 생기면 부품 같이 교환이 가능함.
- 하지만 클라이언트와 서버가 같은 암호 기술을 사용해야 통신이 가능하므로 주의.

#### 6) SSL과 TLS의 차이
- SSL은 넷스케이프 사의 웹 브라우저에 내장되었었고 많은 웹 브라우저에 사용되어 사실상 표준이였다.
- 하지만 3.0 사양에서 푸들 공격(POODLE, 프로토콜 버전 다운 그레이드 공격)이 가능한 취약점이 발견되어 안전하지 않았다.
	- 해당 취약점 사항은 CVE 2014-3566. 보안 취약점과 기타 정보 보안 노출 사항을 기록한 규격화된 목록으로 CVE를 사용하고 뒤 패턴은 발간년도-일련번호이다.
- 이후 TLS는 SSL 3.0을 기초로 하여 IETF가 만든 프로토콜. 따라서 TLS 1.0은 SSL 3.1에 해당하는 것. 
- TLS 1.1에서는 AES를 추가했음. 1.2에서는 인증 암호로 GCM과 CCM을 사용함. 더해 HMAC-SHA 256을 이용하고 IDEA, DES를 삭제하였으며 의사난수함수로 SHA-256을 이용하게 되었다.
- 1.3에서는 오래되어 안전하지 않은 MD5, SHA-1, SHA-244, RC4, 3DES 등을 삭제하고 연결 설정 시 왕복 시간을 줄이기 위해 0-RTT(zero round-trip time) 모드를 추가시킴. 그리고 서명 알고리즘으로 ECDSA가 기본으로 추가됨.

### (2) TLS(Transport Layer Security) 프로토콜
#### 1) 개요
- 가장 널리 사용하는 보안 서비스 중 하나. 현재 버전은 1.3, RFC 8446에 정의됨.
- TCP에 의존하는 프로토콜. 구현되는 일반용도 서비스. 

#### 2) TLS 구조
```
[핸드 셰이크 프로토콜][암호명세 변경 프로토콜][경고 프로토콜][HTTP][하트비트 프로토콜]
[                               레코드 프로토콜                               ]
[                                    TCP                                    ]
[                                    IP                                     ]
```
- TLS를 설계할 때는 신뢰성 있는 종단간에 안전한 서비스를 제공하기 위해 TCP를 활용함. TLS는 단일 프로토콜이 아닌 2계층에 걸친 프로토콜. DTLS는 UDP 기반이다.
- 레코드 프로토콜은 운반자. 이 프로토콜에서 오는 메시지는 보통 TCP인 전송 계층의 페이로드.
- 핸드셰이크 프로토콜은 레코드 프로토콜에 대한 보안 매개변수를 제공함. 암호 집합을 설정하고 키와 보안 매개변수를 제공한다. 필요하다면 클라이언트가 서버에 대해, 서버가 클라이언트에 대해 인증된다.
- 암호명세 변경 프로토콜은 암호학적 비밀을 신속하게 보내는 데 사용된다. 경고 프로토콜은 비정상 조건을 알리는 데 사용된다.
- 하트비트 프로토콜은 프로토콜 개채의 가용성을 모니터링 할 때 사용하는 프로토콜이다. 
	- 매번 연결을 재협상하지 않아도 상호간의 연결 지속 신호를 주고받으면서 통신연결을 유지하게 해주는 기능.

#### 3) 핸드셰이크 프로토콜
- **(가) 개요**
	- 이 프로토콜을 이용하여 서버와 클라이언트가 서로 인증하고 암호화 MAC 알고리즘 그리고 TLS 레코드 안에 보낸 데이터를 보호하는데 사용할 암호키를 협상할 수 있음.
	- 모든 응용 데이터를 전송하기 이전에 사용함. 각 메시지는 다음과 같은 3개의 필드로 구성됨.
		- 유형(Type)(1바이트) : 10개의 메시지 중 하나를 나타낸다.
		- 길이(Length)(3바이트) : 메시지의 길이를 바이트로 나타냄.
		- 내용(Content)($\geq$ 0바이트) : 이 메시지와 연관된 매개변수
	- **메세지 유형과 매개변수 목록**
		- **hello_request**
			- 없음
		- **client_hello**
			- 버전, 랜덤, 세션 아이디, 암호도구, 압축방법
		- **server_hello**
			- 버전, 랜덤, 세션 아이디, 암호도구, 압축방법
		- **certificate**
			- 연속된 X.509v3 인증서
		- **server_key_exchange**
			- 매개변수, 서명
		- **certificate_request**
			- 유형, 기관
		- **server_hello_done**
			- 없음
		- **certificate_verify**
			- 서명
		- **client_key_exchange**
			- 매개변수, 서명
		- **finished**
			- 해시값
	- 핸드 셰이킹 프로토콜은 총 4단계이다.
