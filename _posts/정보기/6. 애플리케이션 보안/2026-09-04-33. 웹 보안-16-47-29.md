## 1. 웹 보안 개요
#### 1) 웹 보안 위협
- 대충 웹을 많이 사용하게 되면서 노출이랑 유출이 많이 된다~
- 근데 그 이유는 TCP/IP랑 HTTP가 보안 서비스를 제공하지 않아서 그렇다

#### 2) 웹 트래픽 보안 방법
- 한 가지 방법은 IP 보안인 IPSec를 이용하기. 종단 사용자의 응용에 투명성을 제공함. 그리고 필터링 기능이 있어 선별된 트래픽에서만 보안을 처리하기 때문에 이에 대한 오버헤드만 추가됨.
- 또 다른 범용 해결책은 TCP 위 레벨에 보안을 구현하는 것. 가장 좋은 예시가 SSL(안전 소켓 계층Secure Socket Layer)과 TLS(전송 계층 보안, Transport Layer Security)라고 알려진 후속 인터넷 표준.
- IPSec는 선택적 암호화를 적용하는게 어렵다. 하지만 SSL/TLS는 선택적 암호화를 지원함.

## 2. SSL/TLS
### (1) SSL/TLS의 개요
#### 1) 기본 개념
- 클라이언트 서버 환경에서 TCP 기반 애플리케이션에 대한 종단간 보안 서비스를 제공하기 위해 만들어진 전송계층 보안 프로토콜. 애플리케이션에 대해 독립적이다.
- 대칭키/공개키 암호, 일방향 해시함수, 메시지 인증코드, 의사난수생성기, 전자서명을 조합하여 안전한 통신을 수행함.
- 특정 암호 기술에 의존하지 않는다. 특정 암호가 약하다고 생각되면 부품을 바꾸듯 다른 암호를 선택하면 됨.

#### 2) 클라이언트와 서버
#### 3) SSL/TLS 상의 HTTP
- 예를 들어 웹 브라우저로 신용카드 번호를 보내면 데이터가 클라이언트로부터 서버에게 보내짐. 이 때 도청당하면 정보가 넘어간다.
- 때문에 통신내용을 암호화해주는 프로토콜로 SSL이나 TLS를 사용함. 그리고 SSL/TLS상에 HTTP를 올림.
- 덕분에 HTTP의 통신은 암호화되어 도청을 방지할 수 있다. `https://`로 시작되는 애들.

#### 4) SSL/TLS 보안 서비스
- **기밀성 서비스**
	- DES, RC4 같은 대칭키 알고리즘을 사용하여 제공되며, 이때 사용되는 비밀키는 핸드셰이크 프로토콜을 통해 생성됨.
- **클라이언트와 서버 상호 인증**
	- 연결 과정에 인증을 사용한다. RSA, DSS 같은 전자서명 알고리즘, X.509 공개키 인증서가 사용됨.
- **메시지 무결성 서비스**
	- 해시 알고리즘을 통해 메시지 인증코드를 만들어 메시지에 포함시킨다.

#### 5) 암호 스위트(cipher suite)
- SSL/TLS에서는 사용하는 대칭키 암호, 공개키 암호, 전자서명, 일방향 해시함수 등은 사용하고 있던 암호 기술에 결함이 생기면 부품 같이 교환이 가능함.
- 하지만 클라이언트와 서버가 같은 암호 기술을 사용해야 통신이 가능하므로 주의.

#### 6) SSL과 TLS의 차이
- SSL은 넷스케이프 사의 웹 브라우저에 내장되었었고 많은 웹 브라우저에 사용되어 사실상 표준이였다.
- 하지만 3.0 사양에서 푸들 공격(POODLE, 프로토콜 버전 다운 그레이드 공격)이 가능한 취약점이 발견되어 안전하지 않았다.
	- 해당 취약점 사항은 CVE 2014-3566. 보안 취약점과 기타 정보 보안 노출 사항을 기록한 규격화된 목록으로 CVE를 사용하고 뒤 패턴은 발간년도-일련번호이다.
- 이후 TLS는 SSL 3.0을 기초로 하여 IETF가 만든 프로토콜. 따라서 TLS 1.0은 SSL 3.1에 해당하는 것. 
- TLS 1.1에서는 AES를 추가했음. 1.2에서는 인증 암호로 GCM과 CCM을 사용함. 더해 HMAC-SHA 256을 이용하고 IDEA, DES를 삭제하였으며 의사난수함수로 SHA-256을 이용하게 되었다.
- 1.3에서는 오래되어 안전하지 않은 MD5, SHA-1, SHA-244, RC4, 3DES 등을 삭제하고 연결 설정 시 왕복 시간을 줄이기 위해 0-RTT(zero round-trip time) 모드를 추가시킴. 그리고 서명 알고리즘으로 ECDSA가 기본으로 추가됨.

### (2) TLS(Transport Layer Security) 프로토콜
#### 1) 개요
- 가장 널리 사용하는 보안 서비스 중 하나. 현재 버전은 1.3, RFC 8446에 정의됨.
- TCP에 의존하는 프로토콜. 구현되는 일반용도 서비스. 

#### 2) TLS 구조
```
[핸드 셰이크 프로토콜][암호명세 변경 프로토콜][경고 프로토콜][HTTP][하트비트 프로토콜]
[                               레코드 프로토콜                               ]
[                                    TCP                                    ]
[                                    IP                                     ]
```
- TLS를 설계할 때는 신뢰성 있는 종단간에 안전한 서비스를 제공하기 위해 TCP를 활용함. TLS는 단일 프로토콜이 아닌 2계층에 걸친 프로토콜. DTLS는 UDP 기반이다.
- 레코드 프로토콜은 운반자. 이 프로토콜에서 오는 메시지는 보통 TCP인 전송 계층의 페이로드.
- 핸드셰이크 프로토콜은 레코드 프로토콜에 대한 보안 매개변수를 제공함. 암호 집합을 설정하고 키와 보안 매개변수를 제공한다. 필요하다면 클라이언트가 서버에 대해, 서버가 클라이언트에 대해 인증된다.
- 암호명세 변경 프로토콜은 암호학적 비밀을 신속하게 보내는 데 사용된다. 경고 프로토콜은 비정상 조건을 알리는 데 사용된다.
- 하트비트 프로토콜은 프로토콜 개채의 가용성을 모니터링 할 때 사용하는 프로토콜이다. 
	- 매번 연결을 재협상하지 않아도 상호간의 연결 지속 신호를 주고받으면서 통신연결을 유지하게 해주는 기능.

#### 3) 핸드셰이크 프로토콜
- **(가) 개요**
	- 이 프로토콜을 이용하여 서버와 클라이언트가 서로 인증하고 암호화 MAC 알고리즘 그리고 TLS 레코드 안에 보낸 데이터를 보호하는데 사용할 암호키를 협상할 수 있음.
	- 모든 응용 데이터를 전송하기 이전에 사용함. 각 메시지는 다음과 같은 3개의 필드로 구성됨.
		- 유형(Type)(1바이트) : 10개의 메시지 중 하나를 나타낸다.
		- 길이(Length)(3바이트) : 메시지의 길이를 바이트로 나타냄.
		- 내용(Content)($\geq$ 0바이트) : 이 메시지와 연관된 매개변수
	- **메세지 유형과 매개변수 목록**
		- **hello_request**
			- 없음
		- **client_hello**
			- 버전, 랜덤, 세션 아이디, 암호도구, 압축방법
		- **server_hello**
			- 버전, 랜덤, 세션 아이디, 암호도구, 압축방법
		- **certificate**
			- 연속된 X.509v3 인증서
		- **server_key_exchange**
			- 매개변수, 서명
		- **certificate_request**
			- 유형, 기관
		- **server_hello_done**
			- 없음
		- **certificate_verify**
			- 서명
		- **client_key_exchange**
			- 매개변수, 서명
		- **finished**
			- 해시값
	- 핸드 셰이킹 프로토콜은 총 4단계이다.
- **(나) 단계별 내용**
	- **HelloRequest**
		- TLS 1.3에서는 삭제된 메세지다. 
		- 서버가 아무때나 보낼 수 있는 메시지. 협상 요구임. 이미 진행중이라면 클라이언트는 이 요청을 무시함.
		- 서버는 이걸 보내고 끝나지 않은 상태에서 또 보내면 안됨.
	- **ClientHello**
		- 처음 연결을 시작하거나 위 메시지에 대한 응답으로 해당 메시지를 보냄.
		- 세션 식별자, CipherSuite 리스트, 클라이언트가 지원하는 압축 알고리즘 리스트, 클라이언트 SSL 버전, 클라이언트가 생성한 난수를 서버에 전달한다.
			- **random :** 클라이언트가 생성하는 32바이트 난수 값으로 Replay 공격을 막기 위한 소금값 역할을 함. 또한 master_secret으로부터 key_block을 생성할 때, 입력값에 포함되어서 각각의 연결마다 비밀키를 새롭게 생성할 수 있다. 
			- **session_id :** 클라이언트가 처음 세션을 생성할 때 empty를 전송하고 재사용할대는 재사용하고자 하는 세션 아이디를 전송함.
			- **cipher_suites :** 키 교환 알고리즘, 암호 알고리즘, MAC 알고리즘을 포함한다. 그 중 하나의 ciphersuite를 선택하게 됨.
				- **ex)** `TLS_RSA_WITH_AES_256_CBC_SHA256` : 키 교환 및 인증 알고리즘으로 RSA를 사용하고 대칭 암호 알고리즘은 AES, 암호 키 길이는 256비트. 블록 암호 모드는 CBC, HMAC용 해시 알고리즘은 SHA-256을 사용하는 cipher suite이다.
	- **ServerHello**
		- ClientHello에 대한 서버의 응답. 실패할 경우 Handshake Failure Alert 메시지를 응답으로 보냄.
		- 해당 메시지는 세션 식별자, 선택한 CipherSuite, 선택한 압축 방법, 서버 SSL 버전, 서버가 생기는 난수를 클라이언트에 전달함.
			- **server_version :** 서버가 지원하는 SSL/TLS 버전과 ClientHello에서 전송받은 client_version(클라이언트가 사용할 수 있는 최상위 버전) 중에 같거나 낮은 걸로 정함.
			- **random :** Replay 공격을 막고 key_block을 만들 때 사용됨.
			- **session_id :** 현재 접속중인 세션 ID. empty를 받으면 새로운 세션 아이디를 전송하며 full Handshake를 진행하고 진행중인 아이디를 받으면 연결을 새로이 생성하는 abbreviate Handshake를 진행한다.
			- **cipher_suite :** 클라이언트로부터 받은 목록 중 하나를 정한다.
	- 여기까지가 단계 1이고, 보안 기능 확립 역할을 한다.
		- 각 클라이언트와 서버는 SSL 버전, 키 교환/메시지 인증/암호화 알고리즘, 압축 방법, 키 생성을 위한 2개의 난수를 알게 된다.
	- **ServerCertificate**
		- 서버의 인증이 필요한 경우에 서버는 ServerHello 뒤에 바로 서버의 인증서가 포함된 Certificate를 보내야 한다. 이 때 인증서는 cipher suite의 키 교환 알고리즘에 맞는 타입이어야 한다.
	- **ServerKeyExchange**
		- 서버의 인증서를 보내지 않았거나 보낸 인증서에 키 교환에 필요한 정보가 부족할 때 전송되는 메시지.
	- **CertificateRequest**
		- 서버는 클라이언트에게 인증함과 동시에 클라이언트의 인증서를 통한 인증을 요구한다. 이 메시지는 선택적으로 사용되지만 사용할 경우 상호 인증이 가능함.
	- **ServerHelloDone**
		- 서버가 보낼 메시지가 다 보냈음을 알려주는 메시지. 클라이언트는 ServerHelloDone이 도착할 때까지 기다림.
	- 여기까지가 단계 2. 서버 인증과 키 교환 후에 서버는 클라이언트에 대해 인증됨. 클라이언트도 선택적으로 서버의 공개 키를 알 수 있음.
	- **ClientCertificate**
		- 서버가 클라이언트의 인증서를 요구했을 경우 클라이언트가 보내는 메시지.
	- **ClientKeyExchange**
		- 클라이언트는 세션키를 생성하기 위해 임의 비밀 정보인 48바이트 pre_master_secret을 생성한다. 그리고 선택된 공개키 알고리즘(RSA, Fortezza, Diffie-Hellman 등)을 이용하여 pre_master_secret을 서버와 공유하게 됨.
		- RSA 키 교환 방법을 이용할 경우, pre_master_secret을 암호화하여 전송하고 DH 또는 ECDH를 이용할 경우 pre_master_secret은 Diffi-Hellman 키 교환 알고리즘에 정의된 방식으로 유도된다.
	- **CertificateVerify**
		- 클라이언트 인증서의 명백한 확인을 위해서 클라이언트는 핸드셰이크 메시지를 전자서명하여 전송함.
	- 여기까지가 단계 3. 클라이언트 인증과 키 교환 후에 클라이언트는 서버에 대해 인증되고 서버와 양측은 사전 마스터 비밀을 알게 됨.
	- **ChangeCipherSpec, Finished**
		- ChangeCipherSpec은 핸드셰이크 프로토콜에 포함되진 않는다. 이 메시지 이후 전송되는 메시지는 새롭게 협상된 알고리즘과 키를 이용할 것을 나타냄.
		- Finished는 위 메시지 이후에 전송되며 협상된 알고리즘과 키가 처음으로 적용됨. 상대편에서 이 메세지를 통해서 협상한 결과를 확인하게 됨.
		- 서버는 ChangeCipherSpec 메시지와 Finished 메시지를 클라이언트에게 보내고 TLS 핸드셰이크 프로토콜 수행을 마치게 됨. 그럼 연결을 통해 애플리케이션 데이터가 전송되기 시작함.
	- 여기까지가 단계 4. 종료 단계 이후 클라이언트와 서버는 데이터를 교환할 준비를 한다.

#### 4) Record 프로토콜
- **(가) 개요**
	- 신뢰하는 전송 서비스를 필요로 하기 때문에 TCP를 사용함.
	- 레코드 프로토콜은 TLS 연결을 위해 2가지 서비스를 제공함.
		- **기밀성(confidentiality) :** TLS 페이로드를 관용 암호화 하는데 쓸 공유 비밀키를 정의함.
		- **메시지 무결성(Message Integrity) :** 핸드셰이크 프로토콜은 또한 메시지 인증 코드(MAC)를 생성하는데 사용할 공유 비밀키를 정의함.
	- 전송할 응용 메시지를 다룰 수 있는 크기의 블록으로 잘라내어 단편화하고, 옵션으로 데이터를 압축하고, MAC을 적용하고, 암호화를 하고, 헤더를 추가하고, 결과를 TCP 단편으로 전송함.
	- 수신된 데이터는 복호화를 하고, MAC을 확인하고 압축을 풀고 재조립하여 상위 계층 사용자에게 전달함.
- **(나) 단계별 절차**
	-  **단편화 (Fragmentation)** 
		- 상위 계층에서 받은 큰 데이터를 다루기 쉬운 일정 크기(최대 16KB)의 블록으로 잘게 나눔.
	- **압축 (Compression)** 
		- 나눠진 데이터 블록을 압축한다. 단 압축 기능은 CRIME 같은 보안 취약점을 유발할 수 있어서 최신 통신 환경에서는 보통 쓰지 않고 생략함.
	- **MAC 추가 (Message Authentication Code)** 
		- 전송 도중 데이터가 변조되지 않았음을 보장(무결성)하기 위해, 해시 알고리즘을 이용해 MAC(메시지 인증 코드)을 계산해서 데이터 뒤에 덧붙임.
	- **암호화 (Encryption)** 
		- 핸드셰이크 과정에서 서로 합의한 대칭키를 사용해서 앞서 만들어진 데이터와 MAC을 통째로 암호화함.
	- **헤더 추가 (Append Header)**
		- 암호화된 블록의 맨 앞에 프로토콜 종류(Content Type), TLS 버전, 길이 정보를 담은 레코드 헤더를 붙여서 전송 계층(TCP)으로 내려보냄.

#### 5) ChangeCipherSpec 프로토콜
- 직전에 협상된 CipherSpec과 키에 의하여 보호될 후속 레코드를 상대에게 알리기 위하여 클라이언트 또는 서버에 의해 전송된다. 
- 종단 간에 협상된 보안 파라미터를 이후부터 적용/변경함을 알리기 위해 사용하는 프로토콜. 예를 들어 이 메시지를 받으면 수신자측에서는 보류된 읽기 상태를 현재 읽기 상태로 변경함.
- 한 바이트로 구성되고 값 1을 갖는 한 개의 메시지로 구성됨.

#### 6) Alert 프로토콜
- 경고 프로토콜은 통신과정에서 발생하는 오류를 통보하기 위해 경고할 때 사용됨.
- Alert 메시지는 경고 메시지와 경고에 대한 상세한 정보를 전달함. 치명적 Alert 레벨 메시지는 연결을 즉시 단절함.
- 이 프로토콜 안 각 메시지는 2바이트로 구성됨. 첫 바이트는 메시지의 엄밀성을 전달하기 위해 경고(warning), 혹은 심각(fatal)이라는 2가지 값을 가짐. 두 번째 바이트에는 특정 경고를 나타내는 코드가 들어있음.

#### 7) 하트비트 프로토콜
- 컴퓨터의 네트워크와 연관해서 하트비트란 정상 동작을 나타내기 위해 시스템의 다른 부분과 동기화 하려고 보내는 주기적 신호.
- 프로토콜 개체의 가용성을 모니터링할 때 사용함.

#### 8) SSL/TLS 공격
- **(가) OpenSSL의 HeartBleed 취약점**
	- OpenSSL 암호화 라이브러리의 하트비트라는 확정 모듈에서 클라이언트 요청 메시지를 처리할 때 데이터 길이 검증을 수행하지 않아 시스템 메모리에 저장된 64KB 크기의 데이터를 외부에서 아무런 제한 없이 탈취할 수 있는 취약점.
	- 원격에서 발생 가능한 취약점. 공격자는 시스템 메모리에 저장된 개인 정보 및 인증 정보 등을 탈취할 수 있음.
		- SSL 서버 비밀 키, 세션키, 쿠키 및 개인정보 등이 노출 가능함. 이는 서비스 환경에 따라 다름.
	- 대응책은 대책이 있는 버전을 사용하거나 해당 확장을 사용하지 않는 옵션으로 재컴파일 하기.
	- 또한 서버 측 SSL/TLS 개인키가 유출되었을 가능성을 배제할 수 없기 때문에 인증서를 재발급 받는걸 검토하고 취약점 조치 완료 후 사용자들의 비밀번호 재설정을 유도.
- **(나) SSL 3.0의 취약점과 푸들 공격**
	- TLS를 사용하고 있어도 SSL 3.0으로 다운그레이드 당하여 푸들 공격을 받을 취약점이 있음.
	- SSLv3.0을 사용하도록 강제한 후 MITM 공격을 통해 암호화되어 송수신되는 쿠키정보나 데이터를 추출하는 것이 가능함. 또한 블록 암호화인 CBC를 사용하는 경우 패딩된 암호블록이 MAC에 의해 보호되지 않는 취약점도 이용함.
	- 효과적인 대책은 SSL 3.0을 사용하지 않는 것.
- **(다) FREAK 공격과 암호 수출 규제**
	- SSL을 통해 강제로 취약한 RSA로 다운그레이드 시킬 수 있는 취약점을 발견함.
	- Factoring RSA Export Keys의 약자로 SSL/TLS 서버에 대한 RSA Export Suites라고 불리는 약한 암호 스위트를 사용하게 하는 공격.
	- MITM 공격을 통해 512비트 RSA로 다운그레이드시킨다.
	- 버전 업뎃이나 OS 및 브라우저도 업그레이드로 대응하기.
- **(라) 완전 순방향 비밀성(PFS, Perfect Forward Secrecy)**
	- 서버의 개인키가 노출되어도 이전 트래픽 정보성의 기밀성은 그대로 유지되는 암호학적 성질. 때문에 통신 내용을 알 수 없다.

### (3) HTTPS와 S-HTTP
#### 1) HTTPS
- HTTP와 SSL의 결합.
- 정상적인 HTTP는 80번 포트를 호출하지만 HTTPS는 443번을 사용하며 SSL을 호출한다. 기밀성 및 클라이언트와 서버의 인증, 데이터 무결성을 제공한다.
- 아래 통신요소가 암호화됨.
	- 요청 문서 URL
	- 문서 내용
	- 사용자가 입력한 브라우저 양식 내용
	- 브라우저가 서버와 주고받은 쿠키
	- HTTP 헤더 내용
- HTTPS는 공격자가 중간에서 스니핑하기 어렵게 만들어주지만 웹 애플리케이션 해킹의 주요 원인인 사용자 입력값에 대한 검증은 하지 못함.

#### 2) S-HTTP
- **(가) 개요**
	- HTTP에 보안 기능을 추가하기 위해 확장됨.
- **(나) S-HTTP의 원리**
	- S-HTTP는 SSL과 달리 HTTP 메시지가 암호화 서명되어 기존 TCP/IP 망을 통해 전송됨.
	- S-HTTP는 컴퓨터 사이에 보내지는 각 메시지를 보호하고, HTTPS는 두 컴퓨터 사이의 통신 채널과 메시지를 모두 보호한다.
- **(다) S-HTTP의 동작**
	- HTTP 트랜잭션의 형태를 유지하고 있기 때문에 기존 HTTP 특성을 유지함.
	- 다양한 암호기능을 지원
	- 협상 과정을 통해 다양한 알고리즘, 모드, 매개 변수 등을 설정할 수 있다.
	- 새로운 프로토콜 지시자로 shttp를 사용함.

#### 2) 관리자 페이지 접근통제
- 웹 애플리케이션의 관리자 페이지가 추측 가능한 형태로 구성되어 있을 경우 공격자가 관리자 페이지를 쉽게 접근할 수 있으며, 브루트 포스 공격을 통해 관리자 권한을 획득할 수 있는 취약점.
- 관리자 IP를 동록하고 해당 아이피로만 관리자 페이지로 접근 가능하도록 하는 아파치 설정은 아래와 같다.
```
<Directory "var/www/html/admin">
 Order Deny,Allow
 Deny from all
 Allow from 192.168.20.1
</Directory>
```
- Order 지시자는 Allow, Deny 순서. 뒤에 오는 설정이 우선이다.
- 웹 서버/페이지 등에 접근하는 사용자를 IP 주소 등을 통해서 통제함.
