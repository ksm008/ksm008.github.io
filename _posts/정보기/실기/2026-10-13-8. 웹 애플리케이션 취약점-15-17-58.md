## 1. SQL 인젝션 취약점
- 웹 애플리케이션에서 입력받아 데이터베이스로 전달하는 정상 SQL 질의를 변조, 삽입하여 불법 로그인 등 여러 비정상 접근을 시도하는 공격기법.
- DB에 악성 사이트를 삽입하여 접근하는 사용자를 피상 사이트, 또는 악성코드 유포 사이트로 유도하거나 OS 명령어 실행, DB 정보 획득 등을 할 수 있다.
- **무료 SQL 인젝션 취약점 스캐너**
	- Nikto
	- SQLMap
	- Absinthe

### (2) 공격방식에 의한 분류
#### 1) Form SQL Injection
- **(가) 개요**
	- 질의문의 조건을 조작하여 인증을 우회함. 조건절인 where절이 항상 참이 되도록 질의문을 조작한다. 
	- 공격 성공 시 반환되는 레코드 셋의 첫 번째 레코드에 해당하는 사용자 권한을 획득하게 됨.
- **(나) 취약한 사이트**
	- SQL 질의문에 사용되는 특수문자(`", ' 등`)을 입력했을 때 에러 메시지가 발생한다면 입력 값이 데이터베이스 서버에 전달되어 처리 중 오류가 발생했다는 것. 
	- 입력값에 대한 검증이 이루어지지 않는 SQL Injection에 취약한 페이지로 볼 수 있음.
	- 공격자가 아이디 파라미터로 `' or 1=1#` 같은 where 절을 무조건 참으로 만드는 입력값을 삽입하면 아래와 같은 SQL문이 만들어지게 된다.
		- `SELECT id, pass FROM member WHERE id='' or 1=1#' AND pass='1234'`
		- `'`를 추가하여 `id=''`를 만들고 or 1=1 때문에 where 절은 무조건 참이 된다. 따라서 모든 레코드가 SELECT 되도록 한다.
		- `#`을 통해 뒤를 주석처리하여(MySQL 주석 문자는 `#`) 비밀번호 조건을 무력화시킨다.
		- MS-SQL, Oracle은 `--`로 주석처리한다.
	- 만약 위 SQL 질의문에 대한 결과로 아래와 같은 결과가 나왔다 하면...
		```
		id pass
		admin 1234
		kiwi11 1111
		kiwi22 2222
		...
		```
		- 취약한 PHP 코드는 대부분 SELECT한 결과에 대해 첫 레코드의 id 필드 정보를 가지고 로그인 ID를 식별한다. 따라서 만약 위 SQL 질의문이 성공했을 경우 가장 위에 있는 admin 계정으로 로그인된다.
- **(다) 안전한 사이트 실습**
	- **php.ini 의 magic_quotes_gpc 설정하기**
		- `magic_quotes_gpc = On`
		- Get, Post, Cookie로 전달되는 데이터에서 `', ", \,` 널문자 등 특수문자를 일반 문자로 치환해준다. 이를 특수문자의 이스케이프 처리라고 한다.
		- 일반문자로 치환하는 방식은 특수문자 앞에 백슬래시(`\`)를 붙이면 특수문자 기능이 제거됨.
		- 근데 최신 PHP 버전 5.4 이상에서는 해당 설정을 더 이상 지원안함; 
	- **mysql_real_escape_string() 사용하기**
		- 때문에 `mysql_real_escape_string()`과 같은 MySQL 라이브러리 함수를 사용해야 함. 해당 라이브러리 함수는 개행문자 등까지도 이스케이프 처리한다.
		- 그러면 `\' or 1=1#` 형태로 변환되어 `' or 1=1` 자체를 아이디로 인식한다.
	- **Prepared Statement(선처리 질의문) 이용하기**
		- 선처리 질의문은 입력값만 매개변수로 전달하고 나머지 질의 부분은 미리 컴파일하여 생성한다.
		- `SELECT id, pass FROM member WHERE id='?' AND pass='?'`
		- 위와 같이 질의문이 ?처리 되어있다.
		- 그러면 저 물음표 자리에 따로 아이디, 비밀번호가 들어가게 되고 `' or 1=1` 자체를 아이디로 인식한다.
	- **파라미터 필터링**
		- SQL 인젝션에 사용될 수 있는 문자열을 필터링할 수 있는 사용자 정의 함수를 생성하여 피할 수도 있다.

#### 2) Union SQL Injection
- **(가) 개요**
	- 유니온 셀렉트 질의를 이용하여 질의 결과를 다른 질의 결과에 결합하여 공격하는 기법이다.
	- 유니온은 2개 이상의 셀렉트 문을 결합할 때 사용함. 이 때 각 셀렉트 문의 필드 개수가 같아야 하며 필드 타입이 호환되어야 한다.
	- 유니온은 2가지 방식이 있다. union all은 질의 결과를 합해서 중복된 결과를 보여주고, 일반 union은 중복을 제거하고 보여준다.
- **(나) 실습**
	- **예시**
		- 폼의 아이디 값에는 `' UNION SELECT 'admin' 'admin'`, 비밀번호에는 admin을 적어준다.*
		- `SELECT id, pass FROM member WHERE id='' UNION SELECT 'admin' 'admin'`
		- 그럼 위 질의문이 생성된다.
		- where절의 id 값을 빈 값으로 설정하여 결과는 존재하지만 값이 없는 빈 레코드로 만든 후, UNION SELECT를 통해 뒤에 빈 레코드에 공격자가 원하는 값을 붙여넣는다. UNION SELECT 이후 문자열을 작성하면 필드에 값을 작성하는 것과 같기 때문.
		- PHP는 보통 레코드의 처음을 쓰기 때문에 PHP는 admin에 대한 비밀번호가 admin인것으로 착각하게 되고, 비밀번호에 적은 admin이 승인된다.
	- 유니온 셀렉트가 성공하려면 선행 select와 후행 select의 컬럼 개수가 일치해야한다. 때문에 선행 셀렉트 문의 컬럼 개수를 파악해야함.
	- order by절을 사용하여 확인할 수 있다. 해당 절은 컬럼 명이나 컬럼 인덱스로 정렬할 때 쓰는 절이다. 인덱스는 1부터 시작한다.
	- `' order by 4 #`같은 방식으로 아이디 값에 집어넣은 후 SQL에러가 발생하는 최소 숫자를 찾으면 해당 테이블에 몇 개의 컬럼이 존재하는지 알 수 있다.

### (3) 공격유형에 대한 분류
#### 1) Error-Based SQL Injection
- **(가) 개요**
	- DB 질의에 대한 에러값을 기반으로 한 단계씩 점진적으로 DB 정보를 획득하는 방법. 클라이언트에서 조작할 수 있는 파라미터에 SQL 질의 관련 특수문자를 삽입하여 SQL 에러가 발생한다면 해당 취약점이 있다고 판단할 수 있음.
	- DB 질의에 대한 에러가 노출되는 취약점을 이용함
	- 요즘은 보안 강화로 인해 에러 값을 거의 노출하지 않음. 과거에 많이 사용함.
	- 아래 사례는 MS-SQL에 해당함.
- **(나) 사례**
	- **테이블, 컬럼 정보 획득**
		- URL : `xxx.php?no' having 1=1--`
		- 리턴값 : `[Microsoft][ODBC SQL Server Driver][SQL Server] 'member.no' 열이 집계 함수에 없고 GROUP BY 절이 없으므로 SELECT 목록에서 사용할 수 없습니다.`
			- having은 GROUP BY나 SUM, COUNT 같은 집계함수와 쓰여야 한다. 하지만 저렇게 단독으로 having을 집어넣으면 문제가 발생한다.
			- 여기서 MS-SQL은 에러 원인을 상세하게 설명해서 문제가 된다. 문제가 발생한 첫 컬럼의 이름을 에러 메시지에 그대로 적어놓는다.
			- 해당 에러로 첫 컬럼의 이름을 알 수 있다.
	- **다음 컬럼 정보 획득**
		- URL : `xxx.php?no=' group by member.no having 1=1--` 
		- 리턴값 : `[Microsoft][ODBC SQL Server Driver][SQL Server] 'member.name' 열이 집계 함수나 GROUP BY 절에 없으므로 SELECT 목록에서 사용할 수 없습니다.`
			- 위에서 첫 컬럼을 알아냈으니 이번에는 GROUP BY로 다시 묶어서 시도한다. 첫 컬럼은 묶였지만 다음 컬럼이 묶이지 않아 두 번째 컬럼의 이름을 에러 메시지에 그대로 적어 출력한다.
	- **버전 정보 획득**
		- URL : `xxx.php?no=' union select @@version,1,1-- ``
		- 리턴값 : `nvarchar 값 'Microsoft SQL Server 2000 - 8.00.194 (Intel X86) Aug 6 2000 00:57:48 Copyright (c) 1988-2000 Microsoft Corporation Personal Edition on Windows NT 5.0 (Build 2195: Service Pack 4) '을(를) int 데이터 형식의 열로 변환하는 중 구문 오류가 발생했습니다.`
			- `@@version`은 MS-SQL에서 현재 구동중인 데이터베이스 서버의 정확한 버전 정보를 담는 내장 변수로 기다란 문자열인 nvarchar 형태를 띈다.
			- 여기서 유니온의 특성을 이용한다. 유니온은 컬럼의 개수와 데이터 타입이 일치해야 한다. 하지만 no 파라미터의 경우 int이고 `@@version`의 형태는 nvarchar이다. MS-SQL은 해당 문자열을 int로 강제 변환해보려 하지만 문자를 숫자로 바꿀 수는 없기 때문에 에러가 발생한다. 
			- 여기서 MS-SQL은 에러가 발생한 해당 문자열 원본을 그대로 에러 메시지에 출력한다.

#### 2) Blind SQL Injection
- **(가) 개요**
	- 에러 메시지를 뱉지는 않으나 DB에게 스무고개하듯 참, 거짓으로 대답할 수 있는 질문을 던져서 정보를 유추해내는 방식이다.
	- 에러 베이스 공격에 비해 많은 비교 과정을 거치기 때문에 취약점 발견 시 자동화 도구를 이용하는 것이 일반적.
- **(나) 실습**
	```php
	// 게시판 검색 요청 시 입력값을 이용해 like 검색을 수행한다. (%는 0개 이상의 임의의 문자를 의미)
	if ($mode=="search"){
	    if(!$search){
	        echo("<script>alert('검색할 단어를 입력해 주세요!!');history.go(-1);</script>");
	        exit;
	    }
	    $sql = "select * from $table where $find like '%$search%' order by num desc";
	~~~
	$result = mysql_query($sql, $connect) or die("<div id=\"sql_error\">".mysql_error()."</div>");
	$total_record = mysql_num_rows($result);
	~~~
	```
	 - `$search`를 게시판 테이블에 질의하여 그 결과를 보여주는 검색 코드.
	 - 외부 입력값을 그대로 사용하기 때문에 공격에 취약함.
	 - 외부값은... 언제나 검증을 해야한다.
	 - **질의 조건의 참/거짓에 따른 반응 확인**
		 - 게시판 검색은 LIKE 구문을 사용한다. 동시에 `%` 문자를 사용하여 0개 이상의 임의 문자를 의미한다. 
		 - 그래서 만약 게시판 검색란에 `' and 1=1#`를 입력하게 되면...
		 - `SELECT * FROM free_board WHERE subject LIKE '%' and 1=1#%;` 의 형태가 된다. 
		 - 여기서 `subject LIKE '%'`은 항상 참이 되는 조건이 된다. 그래서 모든 게시물을 조회할 수 있다.
		 - 하지만 만약 1=2로 바꿔버린다면 항상 거짓이 되므로 아무런 게시물도 조회되지 않을 것이다.
	- **테이블 정보 획득 원리**
		- **기초 지식**
			- **information_schema**
				- 데이터베이스에 대한 메타데이터를 제공하는 스키마이다. 
			- **information_schema.table**
				- 데이터베이스에 대한 모든 테이블 정보를 가지고 있는 테이블, table_type 컬럼의 base table은 사용자가 생성한 테이블을 의미한다.
			- `limit pos, len`
				- 출력 레코드의 개수를 제한하는 함수이다. pos는 시작 행을 의미하며 0부터 시작하고 len은 개수를 의미한다.  만약 `limit 0,1`이라면 첫 번째부터 1개의 레코드를 의미한다. 만약 pos를 1씩 증가시키면 다음 레코드를 하나씩 순서대로 추출할 수 있다.
			- `substr(문자열, pos, len)`
				- 문자열을 pos부터 len만큼 부분 문자열을 추출하는 함수. 여기서 pos는 1부터 시작한다. 왤캐 시작 인덱스가 지네들 맘대로냐... 얘는 select로 나온 결과를 잘라서 한 글자씩 알아낼 때 쓰게 된다. 
				- **예시 :** `substr((SELECT table_name FROM information_schema.table WHERE table_type = 'base_table' limit 0,1),1,1);`
				- 위에서 나온 limit 함수를 같이 사용하였다.
			- 책에서 information_schema.table을 통해 나오는 첫 테이블은 `download`이다.
			- **information_schema.columns**
				- 데이터베이스에 있는 모든 테이블의 컬럼 정보를 가지고 있는 테이블이다. 조건절에 테이블명을 지정하여 해당 테이블 명의 컬럼을 조회할 수 있다.
				- 이것도 limit을 사용해서 하나씩 확인이 가능하다. substr도 사용 가능.
				- **예시** 
					- `SELECT column_name FROM information_schema.columns WHERE tale_name'download' limit 0,1;`
					- `substr((SELECT column_name FROM information_schema.columns WHERE tale_name'download' limit 0,1),1,1);`
			- 책에서 download 테이블에 information_schema.columns를 통해 나오는 첫 컬럼은 `num`이다.
		- **Blind SQL Injection을 통해 테이블 정보 탈취**
			- 이제 위 지식을 바탕으로 테이블 정보를 탈취할 수 있다.
			- 검색란에 `' AND substr((SELECT table_name FROM information_schema.table WHERE table_type = 'base_table' limit 0,1),1,1) = 'a'#`같은 형식을 집어넣는다.
			- 그러면 limit에 의해 첫 테이블인 download가 선택되고 substr에 의해 첫 알파벳인 d가 선택된다. 하지만 d는 조건문에 의해 a와 같지 않으므로 아무런 결과도 나오지 않게 된다.
			- 만약 조건문을 `'d'`바꿔준다면 download의 d와 같아져 해당 테이블에 해당하는 게시물들이 출력된다.
			- 컬럼 정보도 똑같은 방법으로 탈취할 수 있다.
			- POST 방식으로 전달되는 URL 인코딩된 파라미터를 디코딩하면 SELECT, table_name, column_name, substr, limit 등의 값들을 볼 수 있으며 이를 이용한 blind sql injection 공격을 의심해볼 수 있음.
		- **테이블명과 컬럼명을 이용하여 데이터 탈취하기**
			- 내일 작성합시다

## 2. 크로스 사이트 스크립트 취약점
### (1) 개요
- 웹 어플리케이션에서 사용자 입력값에 대한 필터링이 제대로 이루어지지 않을 경우 공격자가 입력이 가능한 폼(웹브라우저 URL 또는 게시판 등)에 악의적인 스크립트를 삽입, 해당 스크립트가 희생자 측에서 동작하도록 하여 악의적인 행위를 수행하는 취약점을 말함.
- 크게 3가지 유형으로 나뉨.
	- Stored XSS
	- Reflected XSS
	- DOM bassed XSS

### (2) Stored XSS(저장형 XSS)
- **(가) 개요**
	- 취약한 웹서버에 악성 스크립트를 저장하고 희생자가 해당 자료를 요청할 때 악성 스크립트가 삽입된 응답 페이지가 전달되어 클라이어트 측에서 동작하는 방식.
- **(나) 취약한 사이트 실습**
	- iframe 태그를 이용하여 자바스크립트를 실행하고 공격자 서버로 사용자 쿠키를 URL 쿼리스트링의 cookie 파라미터로 전달하는 스크립트를 작성하여 게시물로 등록(DB에 저장)
	- iframe의 width, height를 0으로 설정해 희생자가 알 수 없도록 하고 사용자가 클릭하도록 어그로를 끈다.
- **(다) 안전한 사이트 실습**
	- php 코드에 `htmlspecialchars()` 함수를 사용해서 특별한 의미가 있는 특수문자를 이스케이프 처리하고 일반문자로 처리하면 된다.
