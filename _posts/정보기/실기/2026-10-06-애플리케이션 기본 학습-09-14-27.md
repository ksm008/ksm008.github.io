## 1. DNS(Domain Name System)
### (1) DNS 구조
- 사용자 호스트는 DNS 서버에 질의를 하기 전, 로컬 DNS 캐시와 hosts 파일을 검색한다. 만약 여기에도 정보가 없다면 DNS 서버에 질의를 한다. `www.algisa.com`에 접속하는 과정은 아래와 같다.
	- 사용자가 Recursive DNS 서버에 질의한다.
	- Recursive 서버에도 자신의 캐시에 해당 도메인이 없기 때문에 도메인 체계의 가장 최상위인 root DNS에 질의를 한다.
	- root DNS는 해당 도메인의 최종 IP는 모르지만 `.com`을 관리하는 도메인 서버를 알고 있어서 `<com DNS>` 를 Recursive DNS에게 알려준다. 그러면 Recursive DNS 서버는 다시 com DNS 서버에 질의를 하게 된다.
	- com DNS 서버 역시 최종 IP는 모르지만 `algisa.com` 도메인을 담당하는 서버를 알고 있어서 `<algisa.com DNS>` 를 응답한다. 그럼 그 정보를 바탕으로 다시 algisa.com DNS 서버에 질의를 한다.
	- 이번에 질의를 한 algisa.com DNS 서버는 실제 아이피 주소를 관리하고 있는 서버이기 때문에 Recursive DNS 서버에게 정확한 아이피를 응답해준다.

#### 1) 용어정리
- **Recursive/Cache 네임서버/DNS서버**
	- 관리하거나 위임받은 도메인이 없다. 호스트로부터 질의가 들어오면 캐시에 저장된 정보나 반복적 질의를 통해 결과를 사용자 호스트에게 응답해 주는 네임서버다.
	- ISP 업체가 제공 해주는 DNS 서버가 해당한다.
- **Authoritative 네임서버/DNS서버**
	- 특정 도메인에 대한 정보를 관리하면서 해당 도메인에 대한 질의에만 응답해 주는 네임서버.
	- 네임서버가 관리하는 도메인 영역을 Zone/존이라고 하고 관리 도메인에 대한 정보를 담고 있는 파일은 Zone File/존 파일이라고 한다.
	- 네임서버는 존 파일을 읽어 존 데이터를 구성하고 이를 이용하여 질의에 응답한다.
	- 각 회사별로 자신의 도메인을 관리하는 DNS 서버가 해당한다.
- **재귀적 질의(Recursive Query)**
	- 사용자 호스트가 Recursive 네임서버로 질의할 떄 사용하는 방식. 대상 도메인의 리소스 레코드 정보를 조회해서 응답해달라는 질의를 의미함.
	- 그럼 네임서버는 자신의 캐시 데이터를 조회한 후 있으면 그 데이터를 반환하고, 없으면 최상위 Root 네임서버부터 질의 대상 도메인 네임서버까지 반복적 질의를 수행한 후 그 결과를 호스트에게 반환.
- **반복적 질의(Iterative Query)**
	- Recursive 네임서버가 도메인을 관리하는 각 네임서버로 질의할 때 사용하는 방식. 
	- 최상의 루트 네임서버부터 계층구조에 따라 대상 도메인 네임서버까지 각 네임서버가 응답하는 위임된 네임서버 정보에 따라 순차적으로 반복하여 진행하는 질의를 의미.

#### 2) 동작방식 잡것
- **윈도우**
	- 윈도우의 경우 로컬 DNS 캐시, hosts.ics, hosts 파일 순으로 검색하고 없으면 시스템에 설정된 네임서버로 요청한다. 중요한 점은 hosts 파일보다 DNS 질의에 대한 검색 우선순위가 높으므로 질의 시 먼저 참조되는 특성이 있음. 악성코드에 의해 조작된 hosts.ics 파일을 생성하여 파밍 사이트로 접속을 유도하는 보안 사고가 발생한 사례가 있으니 주의해야 한다.
- **리눅스/유닉스**
	- /etc/resolv.conf 파일은 시스템 기본 네임서버 설정 정보를 담고 있음. 내 호스팅 서버의 경우 아래와 같다.
		- `nameserver 127.0.0.53`은 리눅스 운영체제 내부의 로컬 DNS 캐시 데몬인 systemd-resolved를 일차적으로 바라보고 있다는 뜻.
		- `search vcn09260939.oraclevcn.com`은 `ping db-server`처럼 짧은 호스트 이름만 질의하면 운영체제는 자동으로 해당 주소를 붙여서 `db-server.vcn09260939.oraclevcn.com`으로 변환하여 질의한다. 오라클 클라우드 내부망에 있는 다른 인스턴스와 통신하기 편하도록 세팅된 것.
		- `options edns0 trust-ad`는 아래와 같다.
			- `edns0` : DNS 기본 UDP 패킷의 크기는 512바이트로 매우 작음. 이를 확장하여 더 큰 패킷을 주고 받을 수 있게 해주는 옵션. 주로 IPv6나 DNSSEC 암호화 키를 전송할 때 필요함.
			- `trust-ad` : DNS 응답이 중간에 위조되지 않았음을 검증하는 보안 기술인 DNSSEC와 관련된 설정. 응답 패킷 헤더에 있는 AD 플래그를 신뢰하겠다는 뜻. DNS Spoofing(캐시 포이즈닝)의 대표적인 방어 대책이 DNSSEC.
	```
	nameserver 127.0.0.53
	options edns0 trust-ad
	search vcn09260939.oraclevcn.com
	```
	- /etc/hosts 파일은 도메인/호스트명과 아이피 주소 매핑 정보를 담고 있는 파일. 네임서버에 질의하기 전 먼저 참조되는 파일. 파밍 등의 공격을 통해 파밍 사이트로 접속하도록 hosts 파일을 변조하는 사례가 많음. 
	- /etc/host.conf 파일은 DBS 질의 순서를 지정하는 파일로 order 절에 명시된 순서로 질의를 수행한다.

### (3) DNS Lookup 명령어
#### 1) 개요
- DNS Lookup (질의) 유형에는 forward (순방향), reverse (역방향) 룩업이 있다. 
- 순방향은 도메인을 통해서 IP 주소를, 역방향은 IP 주소를 통해서 도메인을 알아내는 질의이다.
- 대표적인 명령으로는 nslookup과 dig 명령이 있음.
- DNS 질의를 위해서는 질의 유형에 대한 이해가 필요함. 질의 유형은 도메인 존 파일에 저장된 각각의 레코드 타입을 말하는 것으로 질의 시에 해당 유형을 지정하면 해당 유형의 응답을 주게 됨.
- 질의 유형은 아래와 같다. 
	- ANY : 도메인에 대한 모든 레코드 질의. 응답이 크기 때문에 DNS 증폭 DRDoS 공격에 악용.
	- NS : 해당 존을 담당하는 네임 서버 질의
	- CNAME : 도메인 이름의 별칭 질의
	- A : 도메인 이름에 해당하는 IPv4 
	- AAAA : 도메인 이름에 해당하는 IPv6
	- SOA : 존의 기본 관리 정보 질의
	- MX : 메일 서버 질의
	- TXT : 도메인에 대한 텍스트 정보 질의. 텍스트 레코드에는 대표적으로 SPF(발송자 메일서버 인증) 레코드 정보가 있다. 요청 대비 응답이 크기 때문에 DNS 증폭 DRDoS 공격에 악용된다.
	- PTR : IP 주소를 가지고 도메인 반환 (리버스 존에 설정된 PTR 레코드 질의)
	- AXFR : 존 버전에 상관없이 무조건 존 전송 요청. Full Zone Transfer
	- IXFR : 존 버전을 비교하여 상위 버전일 경우 존 전송 요청. (Incremental Zone Transfer)
	- HINFO : 호스트의 CPU, OS 정보를 요청한다.

### (4) DNS 스푸핑(Spoofing) 공격
#### 1) 개요
- 공격 대상에게 전달되는 DNS 응답을 조작하거나 DNS 서버의 캐시 정보를 조작하여 의도하지 않은 주소로 접속하게 만드는 공격. 대상은 정상적인 URL로 접속하지만 가짜 사이트로 접속하게 됨. 크게 2가지로 나뉜다.
	- 스니핑을 이용한 DNS 스푸핑
	- DNS 캐시 포이즈닝
- DNS 스푸핑은 DNS 질의/응답에 사용하는 UDP의 비연결 특성 취약점을 이용한 공격. 클라이언트는 DNS 서버와 연결 상태를 유지하지 않기 때문에 DNS 질의/응답을 식별하기 위한 트랜잭션 아이디, 출발지/목적지 주소(아이피, 포트)만 일치하면 먼저 수신한 응답을 신뢰하고 이후 수신한 응답을 모두 폐기하는 것을 이용한 공격.

#### 2) 스니핑 기반의 DNS 스푸핑 공격
- **(가) 개요**
	- 도청중이다가 DNS 응답을 네임서버보다 먼저하는 방식
- **(나) 실습**
	- 더미 허브에 모두 연결되어 있어 무차별 모드(Promiscuous Mode)로 동작 시 스니핑이 가능함. 스위칭 환경에서는 ARP Spoofing 등의 방법으로 스니핑한다.

#### 3) DNS Cache Poisoning 공격
- **(가) 개요**
	- DNS 서버의 캐시 정보를 조작하는 공격임.
	- 서버 자체를 공격하기 때문에 DNS 서버의 캐시 정보가 일정 시간 유지되는 동안 해당 서버에 접근하는 다수의 사용자가 조작된 DNS 응답을 수신하여 대규모의 보안 사고가 발생 가능.
- **(나) 공격 방식**
	- 공격자는 공격 대상인 Recursive DNS 서버에 조작할 도메인 질의를 다수 보낸다.
	- 대상 서버가 반복적 질의를 수행하는 동안 다수의 조작된 DNS 응답을 보냄. 
		- 대상 서버가 사용하는 트랜잭션 아이디와 출발지 포트를 모르기 때문에 랜덤한 값으로 다수 생성하여 응답한다.
		- 스니핑이 가능하면 그걸 쓰면 되지만 불가능한 상황으로 가정함.
	- 조작된 응답 중 정상 응답보다 먼저 일치하는 게 있으면 그 주소가 대상 서버의 캐시에 저장되고 이를 질의하는 사용자는 조작된 사이트로 접속하게 됨.
- **(다) 대응책**
	- 네임서버의 소프트웨어(예 : Bind DNS)를 최신 버전으로 유지하기.
	- 도메인 관리용 서버(Authoritative 네임서버)는 재귀적 질의를 허용하지 않도록 하고 제한된 사용자가 사용하는 Recursive DNS 서버라면 해당 사용자로 제한해서 허용하도록 함.
	- DNSSEC(DNS Security Extensions) 기술 활용
		- 기존의 DNS에 공개키 암호화 방식의 보안 기능을 추가하여 DNS의 보안성을 대폭 강화하는 역할을 함.

### (5) DNS 서버(Bind DNS) 보안
#### 1) 마스터/슬레이브 네임서버 이해하기
- 도메인 네임서버는 도메인의 존 데이터 관리 측면에서 원본 존 데이터를 관리하는 마스터와 이를 동기화해서 사용하는 슬레이브 네임서버로 구분함.
- 마스터에 있는 원본 존 데이터를 슬레이브가 동기화하는 작업을 존 전송(Zone Transfer)이라 한다. 존 전송은 일반적으로 많은 존 데이터가 이동해야 하므로 신뢰성 있는 보장을 전송하는 53/TCP를 이용한다.
- 마스터와 슬레이브는 서로 동일한 기능을 수행한다. 부하 분산을 통해 안전성을 높임.
- 1차 네임서버로 질의해서 응답이 없거나 에러가 발생하면(REFUSED) 2차 네임서버로 다시 질의한다. 
- 리졸버 : 네임서버로 질의를 수행하여 그 결과를 응용 프로그램에 반환해주는 소프트웨어 모듈/라이브러리를 말함.

#### 2) 존 파일 이해하기
- 네임서버 설정(named.conf)에 존 설정을 한다. 서비스는 bind를 사용한다.
- 우분투에서는 bind9을 사용하고 설정 파일 경로는 `/etc/bind/named.conf`이다.

![](assets/img/_blogImage/Pasted%20image%2020261007104229.png)

- 일반적으로 zone 파일은 뒤 확장자가 .zone, 리버스 존 파일은 .rev로 설정한다.


![](assets/img/_blogImage/Pasted%20image%2020261007104151.png)

- 존 파일의 리소스 레코드 형식은 다음과 같다.
	- `host_name [TTL] class record_type data`
		- **host_name :** 등록할 호스트명
		- **TTL :** 레코드의 TTL 값. 미지정시 default 값 (`$TTL값`)을 적용받음.
		- **class :** 인터넷 클래스를 의미하는 IN 지정
		- **record_type :** 레코드 유형을 지정.
		- **data :** 레코드 유형에 따른 데이터 설정.
- 레코드 유형은 이전에 설명했던 질의와 겹친다. 그 외 것들을 적어보면...
- 아니 이거 웃긴게 bind9에서는 옵션 구문 설정을 따로 bind.conf.options 파일에 나누어서 한다...

![](assets/img/_blogImage/Pasted%20image%2020261007105546.png)

- 주요 설정은 아래와 같다.
	- **directory :** 캐시나 임시파일을 저장하는 기본 작업 경로. 
	- **forward :**  forwarders 옵션과 같이 사용됨. only는 자신에게 들어온 도메인 질의를 지정한 다른 서버에 넘김. 다른 서버가 그에 대한 응답이 없을 경우 그 질의에 대해 응답하지 않는 경우에 설정. first는 타 서버에서 응답이 없을 때 자신이 응답.
	- **forwarders :** 모르는 도메인 질의가 들어왔을 때 질의를 전달할 상위 DNS 서버를 지정함.
	- **allow-query :** 질의를 요청할 수 있는 클라이언트를 제한한다.
	- **allow-transfer :** 존 전송을 허용할 대상을 제한한다. any를 쓰게 되면 누구나 다 내부 네트워크 구조를 알 수 있으니 주의.
	- **recursion :** 클라이언트가 요청한 도메인을 끝까지 쫓아가서 알아내 줄지 여부를 설정함. yes면 끝까지 찾아서 답을 주고 no면 자신이 관리하는 존 파일 정보만 대답한다.
	- **listen-on :** bind 데몬이 53번 포트로 질의를 대기할 네트워크 인터페이스를 정의한다. 특정 아이피에서만 요청을 받고 싶을 때 씀.
	- **blackhole :** 블랙홀 기능.
	- **dump-file / statistics-file :** DNS 서버의 캐시 정보나 통계 데이터를 파일로 저장할 때 경로를 지정. 서버 상태를 모니터링하거나 장애를 분석할 때 사용하는 파일...
	- **version :** 그대로 두면 현재 사용중인 버전을 노출한다. Unknown 같은 문자열로 바꿔서 가리는 편.

#### 3) 재귀적 질의에 대한 제한
- 재귀적 질의는 DNS Cache Poisoning 공격에 노출이 쉬움. 때문에 접근제어를 해줘야 한다.
	- `allow-recursion {none;};` 이나 `recursion no` 로 재귀적 질의를 거부할 수 있음.
	- `allow-recursion {127.0.0.1;192.168.56.0/24;};` 처럼 재귀적 질의를 허용할 아이피나 아이피 대역을 명시할 수 있음.
	- 또는 acl을 정의하고 해당 항목에 리스트명을 명시할 수도 있음.

	```
	# 옵션 구문보다 먼저 선언해야 함
	acl "internal" {
	    127.0.0.1;           # 로컬호스트 허용
	    192.168.1.0/24;      # 내부 네트워크 대역 허용
	    10.0.0.0/8;          # 필요한 대역폭 추가 가능
	};
	
	options {
	    directory "/var/cache/bind";
	    
	    # ... 다른 설정들 ...
	    
	    # 위에서 만든 acl 이름을 지정
	    allow-recursion { internal; }; 
	};
	```
	- 재귀적 질의를 제한하면 `Can't find [도메인]: No answer`과 같은 응답이 반환된다.

#### 4) 존 전송에 대한 제한
- `allow-transfer {none;};`은 존 전송을 허용하지 않는거고, 안에 슬레이브 주소 값을 넣으면 그 주소만 존 전송이 가능한 것.
- dig 명령의 axfr/ixfr 질의유형을 통해 존 전송 허용 여부를 테스트할 수 있음. 

## 2. HTTP
### (1) 개요
- HTTP는 웹 상에서 클라이언트/서버 간에 통신을 위해 개발된 프로토콜. 
- 1.0은 비연결형, 1.1부터는 연결형.
- 주로 80/tcp를 사용.
- 클라이언트 요청과 서버 응답으로 이루어짐.
- 1.0 버전까지는 응답 이후 TCP 연결을 바로 종료했음. 제한된 서버 연결 자원을 이용하여 최대한 많은 클라이언트의 요청을 처리하기 위함.
- 서버 입장에서는 통신을 위한 다수의 TCP 연결 설정 및 종료에 대한 부하가 있었다.
- 때문에 1.1 버전부터는 Connection 헤더에 Keep-Alive 옵션이 추가되었다. TCP 연결 상태를 웹 서버 설정에 따라 일정 시간 지속시키는 옵션으로 단 한 번의 연결 이후에 요청/응답을 반복할 수 있음.
- 아파치 웹 서버 설정 파일 (httpd.conf)의 Keep-Alive 관련 설정을 살펴보면 다음과 같다.
	- 지속 연결시간 15초, 연결을 지속하는 동안 허용할 최대 요청 건수는 100건.

	```
	KeepAlive On
	MaxKeepAliveRequests 100
	KeepAliveTimeout 15
	```
	
- 또한 HTTP는 상태를 유지하지 않는다, 동일 클라이언트의 현재 요청과 이전 요청을 식별하지 못함. 근데 서비스 특성상 클라이언트의 상태정보 유지가 필요할 수 있음.
- 상태정보를 유지하기 위해서 쿠키와 세션을 사용한다.

### (2) 클라이언트 상태정보 유지 기술
- **(가) 쿠키 방식**
	- 쿠키는 클라이언트 상태정보를 HTTP 요청/응답헤더에 담아 전달하는 작은 정보/데이터를 말한다.
	- 서버에서 Set-Cookie 응답헤더를 통해 쿠키를 설정하여 클라이언트로 전달하면 클라이언트는 Cookie 요청헤더를 이용해 지속해서 쿠키를 전달하는 형태로 동작한다.
	- 지속 시간에 따라 영속 쿠키와 세션 쿠키로 구분할 수 있다. 
		- 영속 쿠키 : 클라이언트에 파일형태로 지속해서, 또는 일정 시기간 존재하는 쿠키로 설정된 사이트 요청 시마다 쿠키 요청 헤더에 쿠키 정보를 담아서 전달한다.
		- 세션 쿠키 : 클라이언트 메모리상에 세션이 유지되는 동안 존재하는 쿠키로 세션이 종료되면 소멸한다. 일반적으로 웹 브라우저 종료 시 소멸함.
	- 쿠키 방식은 정보를 클라이언트에 저장하고 HTTP 요청/응답 헤더에 담아서 전달하기 때문에 해킹 및 스니핑 공격에 의한 변조와 외부 노출에 취약한 특성이 있음.
	- 중요 정보는 쿠키 방식이 아닌 서버에 정보를 저장하는 세션 방식이 안전하며 쿠키는 암호화를 사용해야 한다.
- **(나) 세션 방식**
	- 서버에 클라이언트 정보를 저장한다.
	- 개별 클라이언트 세션을 구분하기 위해 세션 아이디를 부여하고 세션 아이디는 세션 쿠키를 이용하여 클라이언트와 서버 간에 주고 받음.
	- 상태를 서버에 저장하기 때문에 쿠키 방식에 비해 보안상 안전하다는 장점이 있음.
	- 근데 또 공격자가 세션 아이디를 탈취하면 위장 접근이 가능함. 이걸 HTTP 세션 하이재킹이라고 함.

### (3) HTTP 쿠키 관련 보안 속성
- **(가) httponly 속성**
	- Set-Cookie 응답헤더에 설정하는 속성으로 클라이언트에서 스크립트를 통해 해당 쿠키에 접근하는걸 차단해주는 속성.
	- 헤더에 값을 추가할 경우에는 세미콜론을 구분자로 추가함.
	- 세션 아이디를 저장하고 있는 세션 쿠키를 탈취하는 공격인 XSS 공격에 대응하기 위해서 사용함.
- **(나) secure 속성**
	- 클라이언트에서 HTTPS 통신일 경우에만 해당 쿠키를 전송하고 HTTP 통신일 경우에는 전송하지 않는 속성. 전송 중 평문 쿠키가 노출되는 것을 방지하기 위한 목적. 쿠키에 대한 기밀성을 보장하기 위한 목적으로 사용함.
