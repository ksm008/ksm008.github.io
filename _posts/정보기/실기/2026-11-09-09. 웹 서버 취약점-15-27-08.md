## 1. 디렉터리 리스팅 취약점
- 웹 애플리케이션을 사용하고 있는 서버의 미흡한 설정으로 인해 인덱싱 기능이 활성화 되어 있으면 강제 브라우징을 통해 서버 내의 모든 디렉터리 및 파일 목록을 볼 수 있는 취약점을 말함.
- 구조 뿐만 아니라 백업 파일이나 공개되어서는 안되는 파일 등이 노출 될 수 있음.
- 특정 페이지(`list.php`)가 아닌 아예 디렉터리(`/home/board`)를 요청하는 경우가 해당함.
- **대응책**
	- **httpd.conf 수정**
		- `Options Indexes`에서 인덱스를 `None`으로 변경하면 된다.
		- 모든 디렉터리 섹션의 Options 지시자의 해당 설정을 제거.

## 2. 웹 서비스 메서드 설정 취약점
- GET, POST 메서드 외 다른 불필요한 메서드를 허용할 경우 공격자가 이를 악용하여 웹 서버에 악성 파일을 생성 또는 중요 파일을 삭제할 수 있다.
- OPTIONS 메서드 요청 메시지를 생성하면 해당 웹 서버에서 지원하는 메서드 리스트를 보여준다. 
- **대응책**
	- **httpd.conf 수정**
		```
		<LimitExcept GET POST>
			Order allow, deny
			deny from all
		</LimitExcept>
		```
		- LimitExcept 지시자를 사용하여 불필요한 메서드 사용을 제한한다. 위는 GET, POST를 제외한 지시자를 접근거부한다는 뜻.


## 3. 관리자 페이지 노출 취약점
- 웹 어플리케이션의 전반적인 기능 설정 및 회원관리를 하는 관리자 페이지의 이름을 추측하기 어렵게 해야 한다. admin, manager, webmaster.php 같이 대놓고 알려주는게 아니라 amdfsadfas.php 같이 추측하기 어렵게 해야 한다.
- 또한 관리자 페이지에 대한 접근 설정을 해야 한다.
	- **httpd.conf 수정**
		```
		<Directory "/var/www/html/admin">
			Order Deny, Allow
			Deny from all
			Allow from 192.168.56.30
		</Directory>
		```
		- 이런식으로 특정 아이피만 허용할 수도 있다.
		- Order Allow, Deny는 블랙, 반대는 화이트로 사용.

## 4. 위치공개 취약점
- 개발 또는 소스코드 수정 시 발생하는 백업, 로그, 압축 파일과 같은 파일들이 애플리케이션에 노출될 경우 공격자가 직접 접근을 요청하여 핵심 정보를 획득할 수 있는 취약점.
- **httpd.conf 수정**
	```
	<Files ~ "\.gz$">
		Order allow, deny
		Deny from all
	</Files>
	```
	- 특정 확장자를 가진 파일에 대해 접근을 차단할 수 있다.

## 5. 검색엔진 정보 노출 취약점
- 검색엔진에 의해 해킹에 필요한 정보가 검색되어 해킹의 빌미가 제공되는 취약점이다.
- 검색로봇이란 검색엔진이 검색 데이터 베이스의 내용을 보충하기 위하여 웹사이트를 검색하여 정보를 가져오는 프로그램. 일반적인 검색로봇은 사이트를 방문 시 가장 먼저 robots.txt를 확인하고 이를 준수하여 컨텐츠를 수집함. 악의적인 사이트는 이를 무시하고 컨텐츠를 수집함.
	- **robots.txt**
		- 로봇의 이름을 적는 부분인 User-Agent와 URL 접근허용 여부를 적는 Allow, Disallow로 구분됨.
		- 이때 이 파일은 반드시 웹사이트의 루트 디렉터리에 저장되어야 한다.
		- `User-agent: *` : 모든 로봇에 대해 설정하는 접근허용 여부이다. 특정 로봇의 이름을 지정할 수도 있다. 2개의 로봇을 지정할 때는 2줄로 써야한다.
		- `Allow/Disallow`
			- `Allow: / ` : 모든걸 허용함. Disallow면 모든걸 허용하지 않음.
			- 디렉터리 또는 파일을 명시할 수 있음. 디렉터리면 `/var/private/`처럼 써야 한다. 마지막에 슬래시 하나 추가. 
			- 특정 파일 확장자를 막고 싶다면 `Disallow: /*.pdf$`처럼 `*.[확장자명]$` 형태로 써야 한다.
			- 공백과 콜론 사용에 주의해야 한다.

## 6. 기타 웹서버 보안 대책
### (1) 웹 서비스 최소 권한 사용자 운영
- 웹 서버를 루트 권한으로 구동할 경우 애플리케이션 취약점으로 인하여 루트 권한으로 악의적 명령어 도는 코드가 실행될 수 있음.
- 웹 서버 프로세스를 실행할 별도의 사용자 및 그룹을 생성하고 해당 사용자로 시스템을 로그인할 수 없도록 설정한다.
	- 로그인 쉘을 `/bin/false` 또는 `sbin/nologin`
- 이후 httpd.conf에다가 `User`값과 `Group` 값에 해당 사용자와 그룹을 추가한다.

### (2) 심볼릭 링크 사용 설정 제거
- 유닉스나 리눅스 시스템의 경우 심볼릭 링크를 사용할 수 있는데, 이러면 웹에서 허용하는 디렉터리 외에 다른 디렉터리를 참조하는 링크가 존재하는 경우 해당 링크를 액세스 하는 경우가 발생할 수 있음.
- 만약 시스템 자체 루트 디렉터리에 심볼릭 링크를 걸게 되면 웹 서버 구동 사용자 권한으로 모든 파일 시스템의 파일에 접근이 가능해지므로 문제가 된다.
- `httpd.conf`에 디렉터리 설정 Option 지시자가 만약 `FollowSymLinks`로 되어있으면 `None`으로 고친다.

### (3) 웹 서비스 정보 숨김
- 클라이언트와 웹 서버가 통신하는 경우 응답 헤더, 에러 메시지 등에 웹 서버 버전/종류나 운영체제 버전/종류 등을 전송함.
- 공격자가 버전별로 잘 알려진 취약점을 이용하는데 사용할 수 있으므로 웹 서버의 버전과 같은 배너 정보를 숨기는게 좋다.
