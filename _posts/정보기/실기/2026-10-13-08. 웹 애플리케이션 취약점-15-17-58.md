## 1. SQL 인젝션 취약점
- 웹 애플리케이션에서 입력받아 데이터베이스로 전달하는 정상 SQL 질의를 변조, 삽입하여 불법 로그인 등 여러 비정상 접근을 시도하는 공격기법.
- DB에 악성 사이트를 삽입하여 접근하는 사용자를 피상 사이트, 또는 악성코드 유포 사이트로 유도하거나 OS 명령어 실행, DB 정보 획득 등을 할 수 있다.
- **무료 SQL 인젝션 취약점 스캐너**
	- Nikto
	- SQLMap
	- Absinthe

### (2) 공격방식에 의한 분류
#### 1) Form SQL Injection
- **(가) 개요**
	- 질의문의 조건을 조작하여 인증을 우회함. 조건절인 where절이 항상 참이 되도록 질의문을 조작한다. 
	- 공격 성공 시 반환되는 레코드 셋의 첫 번째 레코드에 해당하는 사용자 권한을 획득하게 됨.
- **(나) 취약한 사이트**
	- SQL 질의문에 사용되는 특수문자(`", ' 등`)을 입력했을 때 에러 메시지가 발생한다면 입력 값이 데이터베이스 서버에 전달되어 처리 중 오류가 발생했다는 것. 
	- 입력값에 대한 검증이 이루어지지 않는 SQL Injection에 취약한 페이지로 볼 수 있음.
	- 공격자가 아이디 파라미터로 `' or 1=1#` 같은 where 절을 무조건 참으로 만드는 입력값을 삽입하면 아래와 같은 SQL문이 만들어지게 된다.
		- `SELECT id, pass FROM member WHERE id='' or 1=1#' AND pass='1234'`
		- `'`를 추가하여 `id=''`를 만들고 or 1=1 때문에 where 절은 무조건 참이 된다. 따라서 모든 레코드가 SELECT 되도록 한다.
		- `#`을 통해 뒤를 주석처리하여(MySQL 주석 문자는 `#`) 비밀번호 조건을 무력화시킨다.
		- MS-SQL, Oracle은 `--`로 주석처리한다.
	- 만약 위 SQL 질의문에 대한 결과로 아래와 같은 결과가 나왔다 하면...
		```
		id pass
		admin 1234
		kiwi11 1111
		kiwi22 2222
		...
		```
		- 취약한 PHP 코드는 대부분 SELECT한 결과에 대해 첫 레코드의 id 필드 정보를 가지고 로그인 ID를 식별한다. 따라서 만약 위 SQL 질의문이 성공했을 경우 가장 위에 있는 admin 계정으로 로그인된다.
- **(다) 안전한 사이트 실습**
	- **php.ini 의 magic_quotes_gpc 설정하기**
		- `magic_quotes_gpc = On`
		- Get, Post, Cookie로 전달되는 데이터에서 `', ", \,` 널문자 등 특수문자를 일반 문자로 치환해준다. 이를 특수문자의 이스케이프 처리라고 한다.
		- 일반문자로 치환하는 방식은 특수문자 앞에 백슬래시(`\`)를 붙이면 특수문자 기능이 제거됨.
		- 근데 최신 PHP 버전 5.4 이상에서는 해당 설정을 더 이상 지원안함; 
	- **mysql_real_escape_string() 사용하기**
		- 때문에 `mysql_real_escape_string()`과 같은 MySQL 라이브러리 함수를 사용해야 함. 해당 라이브러리 함수는 개행문자 등까지도 이스케이프 처리한다.
		- 그러면 `\' or 1=1#` 형태로 변환되어 `' or 1=1` 자체를 아이디로 인식한다.
	- **Prepared Statement(선처리 질의문) 이용하기**
		- 선처리 질의문은 입력값만 매개변수로 전달하고 나머지 질의 부분은 미리 컴파일하여 생성한다.
		- `SELECT id, pass FROM member WHERE id='?' AND pass='?'`
		- 위와 같이 질의문이 ?처리 되어있다.
		- 그러면 저 물음표 자리에 따로 아이디, 비밀번호가 들어가게 되고 `' or 1=1` 자체를 아이디로 인식한다.
	- **파라미터 필터링**
		- SQL 인젝션에 사용될 수 있는 문자열을 필터링할 수 있는 사용자 정의 함수를 생성하여 피할 수도 있다.

#### 2) Union SQL Injection
- **(가) 개요**
	- 유니온 셀렉트 질의를 이용하여 질의 결과를 다른 질의 결과에 결합하여 공격하는 기법이다.
	- 유니온은 2개 이상의 셀렉트 문을 결합할 때 사용함. 이 때 각 셀렉트 문의 필드 개수가 같아야 하며 필드 타입이 호환되어야 한다.
	- 유니온은 2가지 방식이 있다. union all은 질의 결과를 합해서 중복된 결과를 보여주고, 일반 union은 중복을 제거하고 보여준다.
- **(나) 실습**
	- **예시**
		- 폼의 아이디 값에는 `' UNION SELECT 'admin' 'admin'`, 비밀번호에는 admin을 적어준다.*
		- `SELECT id, pass FROM member WHERE id='' UNION SELECT 'admin' 'admin'`
		- 그럼 위 질의문이 생성된다.
		- where절의 id 값을 빈 값으로 설정하여 결과는 존재하지만 값이 없는 빈 레코드로 만든 후, UNION SELECT를 통해 뒤에 빈 레코드에 공격자가 원하는 값을 붙여넣는다. UNION SELECT 이후 문자열을 작성하면 필드에 값을 작성하는 것과 같기 때문.
		- PHP는 보통 레코드의 처음을 쓰기 때문에 PHP는 admin에 대한 비밀번호가 admin인것으로 착각하게 되고, 비밀번호에 적은 admin이 승인된다.
	- 유니온 셀렉트가 성공하려면 선행 select와 후행 select의 컬럼 개수가 일치해야한다. 때문에 선행 셀렉트 문의 컬럼 개수를 파악해야함.
	- order by절을 사용하여 확인할 수 있다. 해당 절은 컬럼 명이나 컬럼 인덱스로 정렬할 때 쓰는 절이다. 인덱스는 1부터 시작한다.
	- `' order by 4 #`같은 방식으로 아이디 값에 집어넣은 후 SQL에러가 발생하는 최소 숫자를 찾으면 해당 테이블에 몇 개의 컬럼이 존재하는지 알 수 있다.

### (3) 공격유형에 대한 분류
#### 1) Error-Based SQL Injection
- **(가) 개요**
	- DB 질의에 대한 에러값을 기반으로 한 단계씩 점진적으로 DB 정보를 획득하는 방법. 클라이언트에서 조작할 수 있는 파라미터에 SQL 질의 관련 특수문자를 삽입하여 SQL 에러가 발생한다면 해당 취약점이 있다고 판단할 수 있음.
	- DB 질의에 대한 에러가 노출되는 취약점을 이용함
	- 요즘은 보안 강화로 인해 에러 값을 거의 노출하지 않음. 과거에 많이 사용함.
	- 아래 사례는 MS-SQL에 해당함.
- **(나) 사례**
	- **테이블, 컬럼 정보 획득**
		- URL : `xxx.php?no' having 1=1--`
		- 리턴값 : `[Microsoft][ODBC SQL Server Driver][SQL Server] 'member.no' 열이 집계 함수에 없고 GROUP BY 절이 없으므로 SELECT 목록에서 사용할 수 없습니다.`
			- having은 GROUP BY나 SUM, COUNT 같은 집계함수와 쓰여야 한다. 하지만 저렇게 단독으로 having을 집어넣으면 문제가 발생한다.
			- 여기서 MS-SQL은 에러 원인을 상세하게 설명해서 문제가 된다. 문제가 발생한 첫 컬럼의 이름을 에러 메시지에 그대로 적어놓는다.
			- 해당 에러로 첫 컬럼의 이름을 알 수 있다.
	- **다음 컬럼 정보 획득**
		- URL : `xxx.php?no=' group by member.no having 1=1--` 
		- 리턴값 : `[Microsoft][ODBC SQL Server Driver][SQL Server] 'member.name' 열이 집계 함수나 GROUP BY 절에 없으므로 SELECT 목록에서 사용할 수 없습니다.`
			- 위에서 첫 컬럼을 알아냈으니 이번에는 GROUP BY로 다시 묶어서 시도한다. 첫 컬럼은 묶였지만 다음 컬럼이 묶이지 않아 두 번째 컬럼의 이름을 에러 메시지에 그대로 적어 출력한다.
	- **버전 정보 획득**
		- URL : `xxx.php?no=' union select @@version,1,1-- ``
		- 리턴값 : `nvarchar 값 'Microsoft SQL Server 2000 - 8.00.194 (Intel X86) Aug 6 2000 00:57:48 Copyright (c) 1988-2000 Microsoft Corporation Personal Edition on Windows NT 5.0 (Build 2195: Service Pack 4) '을(를) int 데이터 형식의 열로 변환하는 중 구문 오류가 발생했습니다.`
			- `@@version`은 MS-SQL에서 현재 구동중인 데이터베이스 서버의 정확한 버전 정보를 담는 내장 변수로 기다란 문자열인 nvarchar 형태를 띈다.
			- 여기서 유니온의 특성을 이용한다. 유니온은 컬럼의 개수와 데이터 타입이 일치해야 한다. 하지만 no 파라미터의 경우 int이고 `@@version`의 형태는 nvarchar이다. MS-SQL은 해당 문자열을 int로 강제 변환해보려 하지만 문자를 숫자로 바꿀 수는 없기 때문에 에러가 발생한다. 
			- 여기서 MS-SQL은 에러가 발생한 해당 문자열 원본을 그대로 에러 메시지에 출력한다.

#### 2) Blind SQL Injection
- **(가) 개요**
	- 에러 메시지를 뱉지는 않으나 DB에게 스무고개하듯 참, 거짓으로 대답할 수 있는 질문을 던져서 정보를 유추해내는 방식이다.
	- 에러 베이스 공격에 비해 많은 비교 과정을 거치기 때문에 취약점 발견 시 자동화 도구를 이용하는 것이 일반적.
- **(나) 실습**
	```php
	// 게시판 검색 요청 시 입력값을 이용해 like 검색을 수행한다. (%는 0개 이상의 임의의 문자를 의미)
	if ($mode=="search"){
	    if(!$search){
	        echo("<script>alert('검색할 단어를 입력해 주세요!!');history.go(-1);</script>");
	        exit;
	    }
	    $sql = "select * from $table where $find like '%$search%' order by num desc";
	~~~
	$result = mysql_query($sql, $connect) or die("<div id=\"sql_error\">".mysql_error()."</div>");
	$total_record = mysql_num_rows($result);
	~~~
	```
	 - `$search`를 게시판 테이블에 질의하여 그 결과를 보여주는 검색 코드.
	 - 외부 입력값을 그대로 사용하기 때문에 공격에 취약함.
	 - 외부값은... 언제나 검증을 해야한다.
	 - **질의 조건의 참/거짓에 따른 반응 확인**
		 - 게시판 검색은 LIKE 구문을 사용한다. 동시에 `%` 문자를 사용하여 0개 이상의 임의 문자를 의미한다. 
		 - 그래서 만약 게시판 검색란에 `' and 1=1#`를 입력하게 되면...
		 - `SELECT * FROM free_board WHERE subject LIKE '%' and 1=1#%;` 의 형태가 된다. 
		 - 여기서 `subject LIKE '%'`은 항상 참이 되는 조건이 된다. 그래서 모든 게시물을 조회할 수 있다.
		 - 하지만 만약 1=2로 바꿔버린다면 항상 거짓이 되므로 아무런 게시물도 조회되지 않을 것이다.
	- **테이블 정보 획득 원리**
		- **기초 지식**
			- **information_schema**
				- 데이터베이스에 대한 메타데이터를 제공하는 스키마이다. 
			- **information_schema.table**
				- 데이터베이스에 대한 모든 테이블 정보를 가지고 있는 테이블, table_type 컬럼의 base table은 사용자가 생성한 테이블을 의미한다.
			- `limit pos, len`
				- 출력 레코드의 개수를 제한하는 함수이다. pos는 시작 행을 의미하며 0부터 시작하고 len은 개수를 의미한다.  만약 `limit 0,1`이라면 첫 번째부터 1개의 레코드를 의미한다. 만약 pos를 1씩 증가시키면 다음 레코드를 하나씩 순서대로 추출할 수 있다.
			- `substr(문자열, pos, len)`
				- 문자열을 pos부터 len만큼 부분 문자열을 추출하는 함수. 여기서 pos는 1부터 시작한다. 왤캐 시작 인덱스가 지네들 맘대로냐... 얘는 select로 나온 결과를 잘라서 한 글자씩 알아낼 때 쓰게 된다. 
				- **예시 :** `substr((SELECT table_name FROM information_schema.table WHERE table_type = 'base_table' limit 0,1),1,1);`
				- 위에서 나온 limit 함수를 같이 사용하였다.
			- 책에서 information_schema.table을 통해 나오는 첫 테이블은 `download`이다.
			- **information_schema.columns**
				- 데이터베이스에 있는 모든 테이블의 컬럼 정보를 가지고 있는 테이블이다. 조건절에 테이블명을 지정하여 해당 테이블 명의 컬럼을 조회할 수 있다.
				- 이것도 limit을 사용해서 하나씩 확인이 가능하다. substr도 사용 가능.
				- **예시** 
					- `SELECT column_name FROM information_schema.columns WHERE tale_name'download' limit 0,1;`
					- `substr((SELECT column_name FROM information_schema.columns WHERE tale_name'download' limit 0,1),1,1);`
			- 책에서 download 테이블에 information_schema.columns를 통해 나오는 첫 컬럼은 `num`이다.
		- **Blind SQL Injection을 통해 테이블 정보 탈취**
			- 이제 위 지식을 바탕으로 테이블 정보를 탈취할 수 있다.
			- 검색란에 `' AND substr((SELECT table_name FROM information_schema.table WHERE table_type = 'base_table' limit 0,1),1,1) = 'a'#`같은 형식을 집어넣는다.
			- 그러면 limit에 의해 첫 테이블인 download가 선택되고 substr에 의해 첫 알파벳인 d가 선택된다. 하지만 d는 조건문에 의해 a와 같지 않으므로 아무런 결과도 나오지 않게 된다.
			- 만약 조건문을 `'d'`바꿔준다면 download의 d와 같아져 해당 테이블에 해당하는 게시물들이 출력된다.
			- 컬럼 정보도 똑같은 방법으로 탈취할 수 있다.
			- POST 방식으로 전달되는 URL 인코딩된 파라미터를 디코딩하면 SELECT, table_name, column_name, substr, limit 등의 값들을 볼 수 있으며 이를 이용한 blind sql injection 공격을 의심해볼 수 있음.
		- **테이블명과 컬럼명을 이용하여 데이터 탈취하기**
			- 내일 작성합시다

## 2. 크로스 사이트 스크립트 취약점
### (1) 개요
- 웹 어플리케이션에서 사용자 입력값에 대한 필터링이 제대로 이루어지지 않을 경우 공격자가 입력이 가능한 폼(웹브라우저 URL 또는 게시판 등)에 악의적인 스크립트를 삽입, 해당 스크립트가 희생자 측에서 동작하도록 하여 악의적인 행위를 수행하는 취약점을 말함.
- 크게 3가지 유형으로 나뉨.
	- Stored XSS
	- Reflected XSS
	- DOM bassed XSS

### (2) Stored XSS(저장형 XSS)
- **(가) 개요**
	- 취약한 웹서버에 악성 스크립트를 저장하고 희생자가 해당 자료를 요청할 때 악성 스크립트가 삽입된 응답 페이지가 전달되어 클라이어트 측에서 동작하는 방식.
- **(나) 취약한 사이트 실습**
	- iframe 태그를 이용하여 자바스크립트를 실행하고 공격자 서버로 사용자 쿠키를 URL 쿼리스트링의 cookie 파라미터로 전달하는 스크립트를 작성하여 게시물로 등록(DB에 저장)
	- iframe의 width, height를 0으로 설정해 희생자가 알 수 없도록 하고 사용자가 클릭하도록 어그로를 끈다.
- **(다) 안전한 사이트 실습**
	- php 코드에 `htmlspecialchars()` 함수를 사용해서 특별한 의미가 있는 특수문자를 이스케이프 처리하고 일반문자로 처리하면 된다.

### (3) Reflected XSS(반사형 XSS)
- **(가) 개요**
	- 외부에 있는 악성 스크립트가 희생자 액션에 의해 취약한 웹 서버로 전달되고 웹 서버의 응답 페이지에서 해당 악성 스크립트가 삽입되어 희생자 측에서 동작하는 방식.
	- 희생자 액션이란 공격자에 의해 조작된 사이트에 접근 시 그 서버에 악성 스크립트를 포함하여 리다이렉트되는 경우나 악성 스크립트가 포함된 링크가 있는 메일을 받은 후 이를 클릭하여 취약한 웹 서버로 요청 정보를 보내는 행위 등을 말함.
	- DB에 스크립트가 저장되는게 아니라 악성 스크립트가 포함된 요청 정보를 처리하는 과정에서 악성 스크립트가 포함된 응답 페이지가 생성되어 희생자에게 전달되는 방식.

### (4) DOM based XSS(DOM 기반 XSS)
- DOM은 문서 객체 모델로 웹페이지 내에 있는 모든 객체를 조작, 관리할 수 있는 계층 형태의 모델.
- 응답 페이지에 포함된 자바스크립트가 동작하면서 DOM 객체를 실행할 때 URL 등에 포함된 악성 스크립트가 동작되도록 한다.
- 저장형 및 반사형 XSS는 응답 페이지에 악성 스크립트가 포함되어 웹브라우저로 전달되어 실행되지만 DOM 기반 XSS는 응답 페이지와 관계없이 웹 브라우저에서 발생한다.

### (5) 취약점 판단기준
- XSS 취약점이 발생할 수 있는 입력 가능한 폼, URL 파라미터 등에 스크립트를 삽입하여 해당 스크립트가 동작하면 XSS에 취약하다고 판단.
- `<script>alert()</script>`같은 예시 코드를 넣어본다.

### (6) 대응책
- 사용자가 입력값 검증을 무조건 서버단에서 하도록 해야한다. 
	- 클라이언트에서 검증을 수행해도 웹 프록시 도구를 이용해 쉽게 우회가 가능함.
	- **웹 프록시 도구**
		- 클라이언트가 요청한 HTTP 요청/응답 정보를 중간에서 가로채 필터링을 우회하거나 서버에 전송되는 데이터를 조작해 허가되지 않는 곳의 정보를 훔쳐보거나 변경, 삽입 등을 가능하게 한다. 파로스, 버프(Paros, Burp) 등이 있음.
- 사용자 입력 문자열에서 HTML 코드로 인식될 수 있는 특수문자를 일반문자로 치환하여 이스케이프 처리한다.
- 만약 게시판에 HTML 태그를 허용해야만 할 경우 HTML 태그 화이트리스트를 만들어 허용하는 방식을 적용한다.

## 3. 크로스 사이트 요청 위조(CSRF:Cross Site Request Forgery)
### (1) 개요
- 웹 어플리케이션에서 정상적인 경로를 통한 요청과 비정상적인 경로를 통한 요청을 서버가 구분하지 못할 경우 공격자가 스크립트 구문을 사용하여 정상적인 사용자가 조작된 요청을 전송하도록 하여 문제를 발생시키는 취약점.
- 공격자가 GET, POST 방식으로 희생자 모르게 공격자의 의도된 행위를 수행한다.
- 사용자의 권한 수준에 따라 피해 범위가 달라질 수 있다.

### (2) 취약점 판단 기준
- 입력가능한 폼에 img 태그의 src 속성을 이용하여 조작된 요청이 실행되면 취약한 것으로 판단한다.

### (3) 대응책
- 웹 애플리케이션에 존재하는 모든 HTTP 요청에 예측할 수 없는 임의 토큰을 추가하여 정상 요청과 비정상 요청을 판별한다.
	- 사용자 접근 권한 정보가 포함된 토큰을 이용하여 세션 정보에 포함된 토큰값과 요청에 포함된 토큰값을 비교함.
	- 중요한 기능에 대해서는 사용자 세션 검증과 재인증을 유도한다.
- XSS에 대한 취약점 또한 제거해야 한다.

## 4. 서버 사이드 요청 위조(SSRF : Server Sode Request Forgery)
### (1) 개요
- 적절한 검증 절차를 거치지 않은 사용자 입력 값을 서버 간의 요청에 사용하여 악의적인 행위가 발생하는 취약점.
- 공격자가 조작된 요청을 웹 서버에 전송하여 웹 서버가 내부 네트워크에 있는 서버에 악의적인 요청을 보내는 취약점이다.

### (3) 대응책
- 사용자 입력값을 다른 시스템의 서비스 호출에 사용하는 경우 사용자 입력 값을 화이트리스트 방식으로 사용해야 한다. 무작위 입력값을 사용한다면 블랙리스트 방식으로 필터링해야한다.
- 동일 내부 네트워크라도 서버 간 인증, 서비스 접근 권한 등을 확인하여 요청을 처리해야 한다.

## 5. 운영체제 명령어 실행 취약점
### (1) 개요
- 적절한 검증을 거치지 않은 경우 사용자 입력 값이 운영체제의 명령어의 일부 또는 전부로 구성되어 실행되는 경우 의도하지 않은 시스템 명령어가 실행되어 부적절하게 권한이 변경되거나 시스템 동작 및 운영에 악영향을 미칠 수 있는 취약점.
	- OS Command Injection으로 부르기도 함. Execution이 아니라...
- `127.0.0.1;cat /etc/passwd` 이런 식으로 명령어를 삽입한다.
	- 세미콜론(;)은 연속 실행, `&&`는 앞 수행이 참일경우 뒤까지 수행 `||`은 앞 수행이 거짓일 경우 뒤를 수행.
- 사용자 입력값을 체크하여 시스템 명령어를 실행할 수 있는 문자를 포함한 경우 경고 메시지를 반환하도록 한다.
- 만약 운영상 운영체제 명령어를 사용해야 한다면 허용할 수 있는 명령어 화이트리스트를 만들어 해당 명령어만 실행할 수 있도록 해야한다.
- 웹방화벽 등 필터링이 가능한 보안장비를 운영한다면 룰셋을 적용한다.
- **PHP에서 사용할 수 있는 운영체제 명령어 실행 함수**
	- 리눅스의 경우 ls, cat 명령
	- 윈도우의 경우 dir, config 등의 명령

## 6. 파일 업로드 취약점
- 업로드되는 파일 타입이나 확장자를 체크하지 않고 허용하는 경우 웹셸이 업로드되어 악의적인 명령이 수행되거나 다운받은 사용자의 PC가 침해사고를 당할 수 있음.
- 웹쉘은 아의적인 목적으로 웹 서버 내의 임의 명령을 실행할 수 있는 스크립트 파일이다. JSP, ASP, PHP 등으로 만들어진다.
- 업로드할 파일타입을 화이트리스트로 허용할 것만 남겨둬야 한다.
- 요청 메시지의 파일 타입 즉 Content-Type 헤더를 허용하는 것으로 바꿔 우회할수도 있다. 때문에 파일 확장자에 대한 추가 검증을 수행하는 것이 더 안전하다.
- 업로드 되는 파일을 저장하기 위한 전용 디렉터리를 별도로 생성하서 만약 악성 파일이 업로드 되더라도 웹 서버 설정을 통해 서버 사이드 스크립트 파일이 실행되지 않도록 하거나 직접 URL 호출을 차단할 수 있다.
	- httpd.conf에 `AllowOverride` 값에 `FileInfo` 또는 `All`을 적고 파일 업로드 디렉터리에 엑세스 파일인 `.htaccess` 파일을 생성한다.
	- 파일 업로드 디렉터리에 액세스 파일을 생성하고 `FilesMatch` 지시자를 이용하여 특정 파일들의 확장자를 차단하도록 설정한다.
	```
	<FilesMatch "\.(ph|inc|lib)">
		Order allow,deny
		Deny from all
	</FilesMatch>
	
	AddType text/html .html .htm .php .php3 .php4 .phtml .phps .in .cgi .pl .shtml .jsp
	```
	- 그리고 `AddType` 지시자를 이용하여 서버 사이드 스크립트 확장자를 가진 파일들에 대해 text/html로 MIME 타입을 재조정하여 PHP 파일이 아닌 HTML 문서로 처리하도록한다.
- 업로드할 파일 크기를 제한해도 좋다. 파일 업로드 디렉터리에 대해 `LimitRequestBody [바이트]`를 지정하면 된다. 만약 크기를 초과하게 될 경우 에러 413을 반환한다.(Request Entity too large)

## 7. 파일 다운로드 취약점
- 파일을 다운로드 받는 기능이 존재하는 웹 어플리케이션이 다운로드 시 파일의 경로 및 파일명을 파라미터로 처리하는 경우 이를 적절히 필터링하지 않으면 공격자가 조작하여 허용되지 않은 파일을 다운로드 할 수 있다.
- 시스템 환경설정 파일이나 소스코드 파일 등을 받을 수 있음.
- 파일 경로를 이동할 수 있는 문자에 대해 블랙 리스트 처리를 한다. (`../ 이나 //\`) 등
- **취약점 판단 기준**
	- 다운로드가 가능한 페이지의 URL이나 파라미터를 조작하여 임의 파일 다운로드가 가능할 경우 취약한 것으로 판단함.
- **대응책**
	- 허용하는 경로 이외의 디렉터리와 파일에 접근할 수 없도록 함.
	- 사용자 입력값에 경로를 변경할 수 있는 문자열을 필터링하도록 웹 애플리케이션 소스 파일을 작성한다.
	- 웹 방화벽 등 필터링 가능한 장비를 운영중이라면 룰셋을 적용한다.

## 8. 경로 추적(Path Traversal) 취약점
- 웹 애플리케이션 파일이나 디렉터리 접근이 통제되지 않아 웹 서버 또는 애플리케이션의 중요한 파일과 데이터에 대한 접근 및 실행이 허용되는 취약점.
- 웹 애플리케이션 루트 디렉터리를 벗어나 시스템의 주요 파일과 데이터에 접근할 수 있는 취약점.
- 상대경로 참조 방식 또는 이를 인코딩한 형태의 문자를 사용하여 다른 디렉터리의 파일을 사용한다.
- 표의 순서는 각각 URL 인코딩, 더블 URL 인코딩, 16비트 유니코드 인코딩이다.

| .         | /         | \          |
| --------- | --------- | ---------- |
| .(%2e)    | /(%2f)    | \\($5c)    |
| .(%252e)  | /(%252f)  | \($255c)   |
| .(%u002e) | /(%u2215) | \\(%u2216) |

- 공격자는 단순 문자 뿐만 아니라 위 인코딩된 문자를 삽입하여 경로 조작을 시도할 수 있다. 어떤 방식으로 요청페이지에서 파라미터를 디코딩하는지 모르기 때문에 가능한 모든 방식을 시도함.
- 사용자 입력 값을 필터링 할 때 경로 조작 문자를 단순 빈 문자로 치환하면 공격자는 이를 쉽게 우회할 수 있다. `../`을 빈칸으로 치환한다치면 `....//` 처럼 그냥 문자를 더 쓰면 되기 때문.
- 따라서 웹 루트 디렉터리보다 상위 디렉터리로 접근이 시도 가능하고 파일에 접근 및 실행이 가능하다면 취약한 것으로 판단한다.
- **대응책**
	- 사용자가 임의로 접근할 수 있는 최상위 디렉터리를 루트 디렉터리로 설정하여 웹 서버의 시스템 루트 디렉터리로 접근하지 못하게 제한해야 한다.
	- 유닉스와 리눅스 시스템의 경우 chroot 기능을 통해 웹 루트 디렉터리를 가상의 루트 디렉터리로 만들어 시스템 루트 디렉터리에 대한 접근을 차단한다.
	- 윈도우 시스템의 경우 새로운 논리 드라이브를 만들어 웹 애플리케이션 루트 디렉터리로 설정함.
	- 경로 조작 문자를 아예 차단하거나 다른 문자열로 치환하도록 하고 웹 방화벽 등 보안장비를 운영중이라면 필터링 룰셋을 적용한다.

## 9. 파일 삽입(File Inclusion) 취약점
- 공격자 서버에 있는 원격 파일을 URL 파라미터에 포함시켜 전달하는 방식처럼 공격자가 악성 스크립트를 서버에 전달하여 악성코드가 실행되도록 하는 취약점.
- 악성 스크립트 파일 위치가 로컬에 위치하는지, 원격에 위치하는지에 따라 나뉜다.
- 로컬이면 LFI, 원격지면 RFI.
- **대응책**
	- **php.ini 설정**
		- `allow_url_fopen = Off`로 설정하여 파일이 URL 형태로 include되지 않도록 설정함.
	- 소스코드에 include, require 등의 구문, 함수가 존재하는지 검증하고 만약 입력값을 통해 파일명이 결정된다면 외부 악의적인 파일이 포함되어 실행되지 않도록 `allow_url_fopen = Off`를 설정한다.

## 10. URL/파라미터 변조 취약점
- 실행 경로에 대해 접근제어를 검사하지 않거나 불완전하게 구현하여 공격자가 URL/파라미터 값을 조작하여 중요 정보에 접근이 가능해지는 취약점.
- SQL 인젝션, 불충분한 인증 및 인가, 크로스 사이트 스크립트 공격에 활용될 수 있다.
- 대응하려면 파라미터 변조 여부를 검증하는 과정이 필요하며 중요한 정보가 있는 페이지는 재인증을 적용한다.

## 11. 불충분한 세션 관리 취약점
- 매번 동일한 세션 ID를 발급하거나 세션 타임아웃을 너무 길게 설정했을 경우 공격자가 다른 사용자의 세션을 재사용하여 해당 사용자의 권한을 탈취할 수 있는 취약점을 말함.
- 웹 프록시를 통해 세션 아이디 정보를 획득하고 탈취한 세션을 이용해 다른 브라우저에서 admin 계정 세션을 가로채기를 성공한다. 이게 HTTP 세션 하이재킹.
- **취약점 판단 기준**
	- 세션 아이디를 분석 및 변조하여 로그인 시도에 성공할 경우임.
- **대응책**
	- **php.ini 설정**
		- `session.gc_maxlifetime = 600`처럼 적절한 타임아웃을 설정한다.
		- 또 `session.cookie_httponly = 1` 설정을 해두면 쿠키에 httponly 속성을 활성화할 수 있다. 그러면 쿠키가 클라이언트 스크립트를 통한 참조가 불가능해진다.
		- `session.cookie_secure = 1`을 통해 secure 속성을 활성화하여 HTTPS 통신일 경우에만 해당 쿠키를 전송하는 옵션.
	- 세션 아이디는 추측할 수 없는 랜덤한 값으로 새롭게 발굴한다.
	- 세션 타임아웃을 통해 요청이 없으면 자동 로그아웃 되도록 한다.

## 12. 정보누출 취약점
- 에러 발생시 에러 메시지나 페이지를 통해 불필요한 정보가 누출될 수 있다.
- `httpd.conf`에서 `ErrorDocument` 정의를 통해 사용자 정의 에러페이지를 설정해줄 수 있다.
	- `ErrorDocument 404 /home/security/error_page.php`
- `php.ini`에서는 `display_errors` 값을 `stderr`가 아닌 `Off`로 설정하여 메시지를 출력하지 않도록 한다.
